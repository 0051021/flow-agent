02

FlowAgent 是什么

双重身份：工具 + 知识容器。工具解决效率，知识解决质量，效率+质量构成飞轮。

产品的双重身份

FlowAgent 不只是一个"AI 生成流程图"的工具。每一次使用都在自然产生结构化的业务知识——企业私有的、经过技术验证的决策记录。竞品可以抄 UI，但抄不走积累的知识。

🔧 工具身份

帮人更快地把业务需求翻译成技术方案。压缩时间，不是替代人。AI 给出 80% 的草稿，技术方修正 20%。

🧠 容器身份

每一次翻译-确认的过程，都在沉淀企业私有的业务知识。用得越多→知识越丰富→AI 越准→审核越轻松→用得更多。

从"工具"到"平台"的关键：当知识积累到一定量级，FlowAgent 从"帮技术方设计方案"进化为"帮业务方自助生成方案"——因为 AI 已经学会了这个企业的做事方式。

三个平台，各司其职

FlowAgent 生态由三个独立但深度集成的产品组成。FlowAgent 定义"做什么"，Skill 平台定义"用什么做"，执行引擎负责"怎么做"。

FlowAgent（业务翻译工具）

核心产品。自然语言→结构化方案，流程图编辑器，人机分工标注，知识工作台。当前全部开发精力在这里。

管控后台（治理控制塔）

Agent 运行时的上帝视角：观察全局、被动审批、主动干预、因果归因。不只是"看 Agent 跑得怎样"，而是"在关键时刻改变运行条件并观察结果"。

Skill 平台（能力基础设施）

原子能力的注册、管理、复用。Skill 标准化程度决定自动化程度——从阶段二到阶段三的关键跳板。

当前阶段：技术方的方案设计工具

FlowAgent 当前处于阶段一，核心用户是技术方。AI 生成的方案不保证正确，业务方缺乏判断能力，但技术方知道哪些步骤不通、哪些工具接不上。

时机场景角色
第一次沟通中业务方描述需求，技术方当场生成初版方案沟通工具
两次沟通之间技术方回去细化方案，发现新问题记下来工作台
第二次沟通前带着修改后的方案确认剩余问题协作载体
核心交互模型：方案是草稿，迭代完成。confirm 是最后一步，在此之前方案永远是草稿。

1. 需求澄清

模糊时弹出澄清卡片。AI 先展示理解，再问 1-3 个关键问题。可跳过。

2. Routing 分类

自动判断 Workflow / Agentic。先判断"是什么"，再决定走哪条路。

3. 可行性 Gate v12

先判断"做不做"，再决定"怎么做"。评估自动化 ROI、数据/系统条件、建议自动化程度。

4. 生成 + 标记 + 确认

生成方案→直接展示→confidence 标记→自由编辑→diff 摘要确认。

可行性 Gate：先判断"做不做" (v12)

来自 Anthropic 的 Agent 设计原则：不是用户说什么 AI 就做什么，而是 AI 先判断这件事应不应该做、应该做到什么程度。一个真正靠谱的助手会先告诉你"这件事该不该做"。这嵌入在生成前的评估中，不是单独的拦截步骤。

✅ 适合自动化

"此场景适合自动化，预计可节省 70% 人工操作。已生成完整方案。"

→ 正常进入方案生成

⚠️ 部分适合

"建议仅自动化数据采集+校验环节，申报提交因涉及海关系统无 API 接口，建议保持人工操作。"

→ 生成部分自动化方案 + 标注人工环节的原因

❌ 不适合

"该审批流程涉及法律签章，监管要求 100% 人工操作，自动化 ROI 为负。建议用模板+提醒代替。"

→ 不生成方案，给出替代建议

评估维度AI 判断什么举例
自动化 ROI搭建成本 vs 节省成本，值不值得做"该流程月均执行 3 次，自动化投入不划算"
系统/数据条件有没有 API 接口、数据源是否可用"ERP 系统无开放 API，无法自动拉取数据"
合规约束监管是否允许自动化"金融审批法规要求人工签字，不可自动化"
自动化程度全流程还是部分环节"前 3 步可自动化，第 4 步需人工判断"
设计原则：可行性评估不拦截用户。结论嵌入生成结果的顶部，用户一眼看到"AI 觉得这个场景适合到什么程度"。如果 AI 建议"不适合"，用户仍可以选择继续生成——AI 给判断，人做决策。这本身就是"增强而非替代"的最佳体现。

为什么分 Workflow 和 Agentic？

核心认知：人类做任何任务都有结构——即使是"做小红书运营"这种开放目标，人类也会先定大步骤（调研→策略→执行→复盘→调整），然后在每步内灵活发挥。所谓"Agentic 任务"不是"没有步骤"，而是"步骤不是预先固定的，每一步的选择取决于上一步的结果"。

Workflow — 追求每步准确

步骤明确，输入输出确定。失败模式：某一步错→后面全错。所以需要逐节点确认。人工介入是节点级的。

报关、报销、审批——SOP 明确，步骤不会因为跑了 10 次就需要改

Agentic — 追求目标达成

有目标但路径不固定。失败模式：可能走弯路但最终可能达到。所以需要阶段级确认。人工介入是里程碑级的。

运营、分析、招聘——天然需要迭代，方案本身预期会根据执行结果进化

为什么混合型不再是第三种类型？大部分真实业务都是"部分步骤确定、部分步骤自主"。与其强行分类，不如让 Agentic 天然包含确定性步骤——在阶段制方案中，有些阶段行动是确定的，有些是 Agent 自主的。

Workflow：节点级的精确控制

Workflow 方案的核心是每个节点都有明确的输入/输出/执行方式。但"精确"不等于"死板"——v11 新增了执行规则和确认策略，让节点从"布尔式确认"进化为"智能介入"。

执行规则（v11 已实现）

每个节点 0-3 条策略性规则，和 description 分离。description 说"做什么"，executionRules 说"怎么做"。
例："文件名容错：支持 .xlsx/.csv/.xls 三种格式"

确认策略（v11 已实现）

人工确认不是布尔值（要/不要），而是一个策略。5 种策略：always / threshold / sampling / rule_based / combined。
例：置信度<95% 或 VIP 客户 或 5%抽检 → 确认

为什么需要确认策略？如果每一份报关单的每个字段都要人工确认，AI 自动化就没有意义。策略有生命周期：初始部署期 always → 稳定期 threshold+sampling → 成熟期仅 rule_based+抽检。随着 AI 准确率提升，系统自动建议降低确认频率。

Agentic：从配置表到阶段制的三次进化

Agentic 方案经历了三次重设计，每次都是因为上一版"用户看不懂"或"无法判断方案跑起来会怎样"。

v1 配置表（4 个 Tab）

目标/技能/约束/评估器。问题：业务方完全看不懂"技能配置"和"评估器指标权重"。技术方也难以判断"这个配置跑起来会怎样"。

v9 策略卡片

目标+简化流程图+约束+成功标准。改善：业务方能看懂了。但：流程图太抽象，缺少时间维度和阶段感。

v3/v11 阶段制（当前）

多阶段时间线+三档评判+审批点。解决：业务方能看到"第几天做什么、什么算好什么算差"。技术方看 Agent 运行架构。

核心洞察：Agentic 任务的确认不是"这步对不对"（Workflow 式），而是"方向对不对"。所以确认触发条件完全不同：milestone（阶段完成）、drift_detect（行为偏离）、budget_gate（预算阈值）、time_gate（定期复盘）、anomaly（异常指标）。

阶段制方案：业务方和技术方看到不同的东西

同一份方案，业务方看"做什么、怎么判断好坏"，技术方看"Agent 怎么运行"。这是因为两个角色的审查维度完全不同——业务方关心"我要不要给 Agent 花钱的能力"，技术方关心"Skill 的 schema 和质量够不够"。

📋 示例：小红书运营（4 阶段 · 90 天）

1-7天 冷启动 每天1条测评，测试标题风格，收集基线

8-21天 策略验证 每天2条，A/B测试发布时间 需审批

22-60天 规模化产出 每日3条，评论互动，每周复盘

61-90天 增长冲刺 热点追踪+合作互推 需审批

每阶段含三档评判：✅好/⚠️警告/❌差+对策 | 退出条件 | 追问

业务方看到的

阶段时间线 · 目标指标(KPI+推理依据) · 执行规则 · 权限边界(哪些事 Agent 能自主决定) · 汇报机制(日报/周报示例) · 内容示例 · 风险评估

技术方看到的

决策循环(OODA：观察→评估→行动→反馈) · Skill 编排(依赖链路/并行分组/失败策略) · 上下文架构(短期/长期/外部) · 触发器与调度

Workflow vs Agentic：驳回语义不同

驳回不是简单的"拒绝"。Workflow 的"退回上一步"是线性回退（因为步骤独立），Agentic 的"重新规划"是策略级回退（因为步骤之间有策略依赖，局部退回没有意义）。这个区别决定了两种方案的确认 UI 必须不同。

Workflow 驳回

  • 修正继续 — 改当前步骤结果，继续
  • 退回上一步 — 线性回退重新执行
  • 人工接管 — 整个节点转人工

Agentic 驳回

  • 修正继续 — 局部修正，继续当前策略
  • 重新规划 — 回到决策点，重新选择策略
  • 人工接管 — Agent 暂停，人工处理

人机协作模型：in / on / off the loop

企业 AI 产品的核心问题不是"AI 能不能做"，而是"人应该站在哪里"。业界有三种经典模式，FlowAgent 的 Workflow 和 Agentic 分别对应前两种。第三种在当前技术条件下不可行。

Human in the loop

人在流程里面，关键步骤必须经过人。

→ Workflow 模式

逐节点验收、白盒可审计、每一步有据可查。
报关单证解析 → [人确认] → 合规校验 → [人确认] → 海关申报

Human on the loop

人在流程上方监督，正常时不介入，异常时拉回来。

→ Agentic 模式

阶段审批、异常告警、兜底机制、主动干预。人始终可以接管。
Agent 自主运营 → 人看数据 → 发现潜力账号 → 追加预算

Human off the loop

人完全不在，全自动运行。

→ 当前不可行

AI 单步准确率 85-90%，5 步串联成功率仅 59%。企业场景出错代价高，"出了事谁负责"没有答案。

核心洞察：人的存在不是瓶颈，是合规要求。解法不是把人移走，而是把人从 in the loop 的每一步移到 on the loop 的关键点——释放带宽但不丢责任。确认策略的演进路径（always → threshold → sampling → rule_based）就是从 in 向 on 逐步迁移。

人造大自然 — 产品的治理框架 (v12)

FlowAgent 不是一个"工具"，而是一套治理体系。类比：FlowAgent 造世界（定义规则），Agent 是生态系统在自行运转，管控后台是上帝视角——观察全局，克制干预，归因结果。

🌍 FlowAgent — 造世界

Intervention 的完整链路：①感知（Agent 收到事件）→ ②评估影响（"预算翻倍意味着什么"）→ ③生成调整方案（不是直接改，是提出方案）→ ④权限判断（是否需要再确认）→ ⑤执行调整 → ⑥复盘归因（"干预后涨粉 +2200，占 73%"）。

多层治理：不止一个"上帝" (v12)

企业不是扁平的。不同层级的人看到的视图不同，能干预的范围也不同。Agent 运行在一个有组织层级、有权力结构的企业环境里——这是纯 Agentic 框架（CrewAI、LangGraph）没有建模的维度。

VP / 老板

看：整体 ROI、战略方向
能改：目标、大额预算、优先级
能停：整个项目

部门主管

看：阶段进展、资源效率
能改：约束、阶段策略、追加资源
能停：本部门 Agent

运营 / 业务方

看：每日执行、内容质量
能做：审批内容、微调参数
能停：紧急暂停（舆情风险）

Agent

在规则内自主执行
感知干预并重新规划
标记"因干预导致的变更"

权限不只是"谁能看什么"，还包括"谁能在运行时改什么"。静态权限（管控后台角色）+ 动态干预权限（方案中标注的可干预性）= 完整的治理模型。

三层改造：干预穿透整个产品栈 (v12)

干预不是"只改管控后台就行"——一个 VP 说"追加预算"，要从设计层穿透到执行层再回到治理层，涉及三个产品的联动。

FlowAgent（设计时）

新增：约束的"可干预性"标注

  • 每个约束/参数标记：可干预 ✅ / 红线不可改 ❌
  • 干预范围上下限（预算 0~50000）
  • 最低权限要求（部门主管 / VP）

技术方审核哪些参数允许运行时干预，红线约束在设计时锁死

执行引擎（运行时）

新增：运行时事件注入 + 重规划

  • 接收 Intervention 事件
  • 校验干预是否在允许范围内
  • 注入 Agent context，触发重规划
  • 标记"因干预导致的策略变更"

管控后台（治理时）

新增：干预面板 + 归因分析

  • 只展示当前方案允许干预的参数
  • 权限校验（对照方案定义）
  • 干预记录（谁/何时/改了什么/为什么）
  • 复盘归因（干预前 vs 干预后）
类比：FlowAgent 定义"哪些物理常数可以调"，执行引擎负责"上帝拨了一下后世界怎么响应"，管控后台是"上帝的控制台"。三层联动，缺一不可。

三层评估体系 — 为什么需要三层？

一个问题：Agent 跑完了，怎么知道"做得好不好"？如果只看最终目标（粉丝涨了没），出了问题不知道哪步出的。如果只看每步工具输出，不知道整体方向对不对。所以需要三层：工具→步骤→目标，从下往上汇总，从上往下定位。

第一层：工具级

"这个工具跑成功了吗"
纯代码逻辑，不需要 LLM。检查输出格式/完整性/质量。
例：采集50条数据，3条时间字段为空

第二层：步骤级

"这步的结果质量行不行"
LLM 从用户约束中自动推导评估标准，用户只需审查。
例：内容符合"活泼年轻化"调性吗？

第三层：目标级

"整体目标达成了吗"
用户只需说"什么算成功"，AI 自动转化为结构化指标。
例：粉丝增长(0.4)+互动率(0.4)+合规率(0.2)

对用户来说，评估器就是"成功标准"。策略卡片中只展示通俗的成功标准，技术方展开后能看到完整的三层评估配置。用户不需要理解"评估器"这个概念。

v6 核心变化：从"强制拦截"到"标记提醒"

之前 AI 生成后强制弹出反问卡片，用户必须逐个回答才能看流程图。三个问题：缺乏掌控感（没看全局就被迫答细节）、重复劳动（反问和画布编辑做同一件事）、不尊重专业判断（技术方看一眼就知道怎么改）。

❌ 之前 (v3/v4)

  • 生成后强制弹出反问卡片
  • 必须逐个回答/跳过才能看流程图
  • 缺乏掌控感、重复劳动

✅ 之后 (v6 已实现)

  • 生成后直接展示流程图
  • 不确定节点黄/红标记 + 摘要
  • 用户自由选择处理方式
  • 确认时安全检查兜底
反问真正有价值的场景：AI 不确定该用什么工具、不确定是否需要人工确认、不确定数据从哪来——这些用户在流程图上看不出来。已经有把握的节点细节？让用户自己在画布上看就行。

知识容器 & 工作台

FlowAgent 的工具能力可以被替代，但沉淀在里面的企业私有知识无法被替代。

自进化机制 — 越用越准 (v6)

类比员工经验积累：新员工做 50 次才能形成的经验，FlowAgent 压缩到 5 次。核心是三层进化——从记住错误，到归纳规则，到主动质疑。这是 to B 产品的核心护城河。

第一层：记忆

记录 AI 初版 vs 用户终版的 Diff。下次不犯同样的错。实现：修正后方案作为 few-shot。

第二层：归纳

从多次修正中提炼通用规则。"涉及客户沟通的步骤默认人工"。LLM 定期归纳。

第三层：判断

初期标记多→中期只标关键的→后期主动质疑："根据过往案例，这步需要审批"。

知识工作台 (v10 新增)

方案设计依赖真实数据和规则，但业务方给的规则往往是理想化的。知识工作台让数据验证在平台内完成：上传文件→描述分析需求→AI 生成代码并执行→结果直接应用到方案。技术方可查看/修改代码（Cursor 式掌控感），业务方只看结果。

核心能力

文件管理（通用/方案专属） · AI 代码生成 · 沙箱执行（Pyodide/Docker） · 结构化报告 · "应用到方案"按钮

应用场景

规则验证 · 数据探索 · 格式转换 · SOP 提取 · 模拟测试

AI 验证模式 (v11 新增设计)

业务方定义的规则只覆盖"正常情况"，真实数据中的边界情况（if-else 的 else）因出现频率低而被忽略。验证模式让技术方在平台内用真实数据验证规则完备性，发现漏洞后直接补全方案——不需要离开 FlowAgent 去写脚本。

模式切换（类 Cursor）

AI 助手面板顶部切换：生成模式（当前）/ 验证模式（新增）。不是独立页面，而是同一个 AI 助手的不同能力。

@ 数据引用（类 Cursor）

企业数据已"挂载"在平台上。用 @文件名 或 @文件夹/ 引用数据，AI 自动读取作为验证上下文。无需手动上传。

两种验证方式

直接分析：规则简单/数据少，AI 直接看数据给结论。
脚本验证：规则复杂/数据大，AI 生成 Python/SQL，技术确认后执行。

闭环：验证发现的问题不停留在对话里——AI 建议补充规则 → 用户确认 → 自动更新节点的执行规则/新增条件分支/插入新节点。"验证"直接驱动方案完善。

Skill 架构

Skill = 一个业务可验收的原子能力单元。
不是"最小技术单元"，而是"最小业务验收单元"。

Skill 切割原则：以"业务可验收点"为边界

Skill 的边界 = 从上一个"业务方能看懂并验收的输出"到下一个。业务方能回答"到这里为止，结果对不对"这个问题。人工确认节点放在 Skill 之间，不是 Skill 内部。

❌ 太厚

"报关处理" = 解析+校验+提交+跟踪
→ 业务方只看到"处理完了"，中间出问题不知道

✅ 正确切法

单证解析→[人工确认]→合规校验→[人工确认]→海关申报
→ 每步输出业务方都能看懂、能判断对不对

Workflow vs Agentic 中 Skill 的角色不同：Workflow 中 Skill 是预先绑定（"第 3 步用合规校验 v2.1"）；Agentic 中 Skill 是授权（"给 Agent 这些能力，它自己决定什么时候用"）。

Skill 平台 + 试运行

Skill 有两种形态：原子 Skill（单个能力单元）和 Skill 编排（多个 Skill 组合）。对 FlowAgent 来说两者没有区别——都是一个输入 schema + 一个输出 schema。Skill 内部是 1 个 API 还是 50 步子流程，那是 Skill 平台的事。

阶段Skill 标准化FlowAgent 能力体验
当前只有名字和描述标注"建议使用 XX Skill"技术方手动搭建
Phase 2有 I/O schemaAI 自动匹配 + 参数映射蓝图+Skill 绑定建议
Phase 3完整标准化试运行联动蓝图+试运行报告
试运行（v10）：模拟演练而非生产执行。用模拟数据跑一遍方案，业务方看到交互预览。AI 生成可执行工作流在企业生产环境中不可靠（10 步工作流成功率仅 35%），所以 FlowAgent 输出是方案蓝图，技术方参考蓝图搭建。
