# 方案 Review 三种结论样例

## 1. 样例一：可以交给技术评审

适用情况：业务图结构清楚，节点类型收敛，SOP/策略字段齐全，分支和连线表达完整，没有未处理追问。

```text
方案 Review
看这版业务图交给技术方会不会误解、漏分支或返工。

┌──────────────────────────────────────────────┐
│ 可以交给技术评审                              │
│ 这只说明业务表达足够清楚，技术侧仍需评估系统对接、 │
│ 自动化边界、数据权限和人工兜底。                 │
└──────────────────────────────────────────────┘

这次 Review 真正确认了什么
已通过 7 项硬规则检查；这里不把它包装成技术通过结论。

● 技术方能看懂每一步的业务职责              已具备
  当前每个节点都能看出需要什么、业务人员怎么处理、最后交付什么结果。

● 分支和例外没有只停留在口头说明里          已具备
  涉及缺资料、升级、续申请等情况时，流程线、输出或策略字段里已有可追踪表达。

● 这不代表技术方案已经通过                  后续评估
  Review 只判断业务表达是否适合交给技术，不判断接口、权限、自动化成本和上线风险。

技术侧下一步会继续看

┌ 让技术侧判断自动化边界
│ 哪些步骤系统能做，哪些必须保留人工确认。

┌ 确认数据和文件来源
│ 每个输入来自系统、文件、邮件还是人工上传，是否需要权限或接口支持。

┌ 把业务条件翻译成实现规则
│ 例如缺资料、高风险、超权限、续申请等条件，后续要落到系统判断、人工审核或任务编排里。

[继续完善]                              [去确认方案]
```

产品要点：

- 不展示一长串全绿检查项
- 明确“可以交给技术评审”不是“技术方案通过”
- 主按钮可用

## 2. 样例二：可以讨论，但建议先补几处

适用情况：业务主线清楚，但有少量字段、分支标签或追问未处理。可以进入讨论，但应该把风险摆出来。

```text
方案 Review
看这版业务图交给技术方会不会误解、漏分支或返工。

┌──────────────────────────────────────────────┐
│ 可以讨论，但建议先补几处                       │
│ 业务主线已经能看懂，但有些条件、字段或追问还可能让 │
│ 技术侧产生歧义。                              │
└──────────────────────────────────────────────┘

需要你先处理的内容
已通过 5 项结构检查，下面只列会影响交付判断的问题。

● 每一步是否知道要什么、交付什么              缺关键项
  共 2 个节点需要补字段：
  登记申请信息（缺 操作步骤、业务规则）；
  判断是否续申请（缺 判断流程、异常/升级条件）。

● 先后顺序和交接条件是否清楚                  建议补充
  1 条连线缺少业务标签，建议补充线上条件或流转含义：
  node-4 → node-5。

● 还有没有业务追问没处理                      建议补充
  1 个追问未答，0 个节点使用了默认建议。

建议下一步

┌ 补齐第三个 tab 字段
│ SOP 节点补操作步骤和业务规则；策略节点补判断依据、判断流程和异常/升级条件。
│ 具体缺口：登记申请信息（缺 操作步骤、业务规则）；
│ 判断是否续申请（缺 判断流程、异常/升级条件）。

┌ 补充连线业务含义
│ 给缺标签的连线补上“资料齐全”“需要补资料”“续申请”等业务条件。

┌ 处理待确认问题
│ 提交技术评审前，建议先回答追问，或明确哪些内容可以暂按默认建议处理。

[继续完善]                              [去确认方案]
```

产品要点：

- 允许继续，但不能只显示“基本可提交”
- 问题必须可定位到节点和字段
- 建议项必须能指导用户去哪里改

## 3. 样例三：先别交给技术

适用情况：缺少关键业务信息，或业务图里仍有路由节点/旧 task kind，技术侧拿到后很容易误解。

```text
方案 Review
看这版业务图交给技术方会不会误解、漏分支或返工。

┌──────────────────────────────────────────────┐
│ 先别交给技术                                  │
│ 当前缺的是技术方理解业务所需的关键信息，直接提交容易返工。 │
└──────────────────────────────────────────────┘

需要你先处理的内容
已通过 3 项结构检查，下面只列会影响交付判断的问题。

● 技术方会不会拿到混乱的节点类型              缺关键项
  这些节点需要调整：
  是否需要续申请、资料是否齐全。
  业务侧只保留 SOP 步骤和策略判断，不保留路由节点。

● 每一步是否知道要什么、交付什么              缺关键项
  共 6 个节点需要补字段：
  登记申请信息（缺 操作步骤、业务规则）；
  核对客户资料（缺 业务规则）；
  判断是否续申请（缺 判断依据、判断流程、异常/升级条件）；
  提交 IMI 申请（缺 输入、输出）；
  同步证书结果（缺 操作步骤）；
  通知业务领取证书（缺 业务规则）。

● 异常、补资料、升级场景会不会漏掉            建议补充
  这些节点提到了条件或升级，但没有明确的出边说明：
  核对客户资料、判断是否续申请。

建议下一步

┌ 先收敛业务节点类型
│ 把“是否需要续申请”“资料是否齐全”这类路由节点改成策略节点；
│ 条件结果放在线标签、输出或策略字段里。

┌ 补齐第三个 tab 字段
│ SOP 节点补操作步骤和业务规则；策略节点补判断依据、判断流程和异常/升级条件。

┌ 把条件分支放到线上
│ 缺资料、续申请、无法判断、需要升级这些结果，都要能在流程线上看出来。

[继续完善]                              [先修复阻塞项]
```

产品要点：

- 主按钮禁用或变成“先修复阻塞项”
- 不能给“去确认方案”的行动暗示
- 必须解释为什么不能交给技术，而不是只说校验失败

## 4. 三种状态的差异

| 状态 | 顶部结论 | 主体内容 | 建议下一步 | 主按钮 |
| --- | --- | --- | --- | --- |
| 可以交给技术评审 | 业务表达足够清楚 | 展示交接边界，不堆全绿项 | 技术侧继续看自动化、数据、权限、接口 | 可点击：去确认方案 |
| 可以讨论，但建议先补几处 | 主线可读，但仍有歧义 | 展示具体问题节点和缺失字段 | 指向要补的 tab、连线或追问 | 可点击：去确认方案 |
| 先别交给技术 | 缺关键业务信息 | 展示阻塞项和具体修复对象 | 先修复节点类型、字段、分支表达 | 禁用：先修复阻塞项 |

## 5. 工程实现提示

Review 输出建议保持同一结构：

```ts
type SchemeReviewResult = {
  level: "ready" | "needs_attention" | "not_ready";
  title: string;
  summary: string;
  items: Array<{
    label: string;
    status: "pass" | "warning" | "block";
    note: string;
  }>;
  suggestions: Array<{
    title: string;
    detail: string;
    level?: "warning" | "block";
  }>;
};
```

展示层规则：

1. `ready` 时，不展开所有 pass 项，只展示业务交接边界。
2. `needs_attention` 和 `not_ready` 时，只展示 warning / block 项。
3. 所有 warning / block 项必须包含具体节点名，字段问题必须包含缺失字段。
4. `not_ready` 时禁用确认按钮。
5. 文案里始终避免把 Review 说成“技术可行性通过”。
