## 一、我们做的是什么

**一句话**：一套覆盖"需求翻译 → 能力编排 → 自动执行 → 持续运维"全链路的企业 AI 自动化平台。

不是又一个 Dify、n8n 或 Coze。那些产品解决的是"怎么搭建和运行 AI 工作流"；我们解决的是**从业务方脑子里的想法到可运行的自动化方案之间的全部断裂**——翻译断裂、协作断裂、执行断裂、知识断裂。

### 四件套一览

| # | 产品 | 一句话定位 | 核心用户 | 当前状态 |
|---|------|-----------|---------|---------|
| 1 | **FlowAgent** | 业务翻译 + 方案设计 + 知识沉淀 | 业务方 + 技术方 | 已有 Demo |
| 2 | **Skill 平台** | 原子能力注册 + 标准化 + 版本管理 | 技术方 + 平台运营 | 规划中 |
| 3 | **执行层（Runtime）** | 方案执行 + 配置外化 + 运行反馈 | 技术方 + 业务方 | 规划中 |
| 4 | **管控后台** | 监控 + 运维 + 人工介入 + 配置变更 | 业务方 + 技术方 + 管理者 | 已有 Demo（Mock） |

### 全景架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        用户层                                    │
│         业务方                技术方              管理者          │
└──────┬──────────────────────┬──────────────────────┬────────────┘
       │ 描述需求              │ 审核方案              │ 看数据
       ▼                      ▼                      ▼
┌─────────────────────────────────────────────────────────────────┐
│  ① FlowAgent — 翻译 + 设计                                      │
│     自然语言 → AI 翻译 → 结构化方案蓝图 → 双角色协作审核           │
│     ┌──────────────────────────────────┐                        │
│     │  知识容器（贯穿四件套的数据中枢）    │ ← 所有产品的知识汇聚于此 │
│     └──────────────────────────────────┘                        │
└──────────────────────┬──────────────────────────────────────────┘
                       │ 确认的方案蓝图 JSON
                       ▼
┌─────────────────────────────────────────────────────────────────┐
│  ② Skill 平台 — 能力供给                                         │
│     原子能力注册（I/O schema）· 版本管理 · 三层可见性              │
│     平台通用 / 社区共享 / 企业私有                                 │
└──────────────────────┬──────────────────────────────────────────┘
                       │ 标准化的 Skill 引擎模板
                       ▼
┌─────────────────────────────────────────────────────────────────┐
│  ③ 执行层 — 跑起来                                               │
│     引擎模板（技术方开发，不常变）+ 外化配置（业务方可改，频繁变）    │
│     Workflow 节点执行 · Agentic 阶段执行 · 试运行 · 生产运行       │
└──────────────────────┬──────────────────────────────────────────┘
                       │ 运行状态 · 日志 · 异常 · 效果指标
                       ▼
┌─────────────────────────────────────────────────────────────────┐
│  ④ 管控后台 — 看得见、管得住                                      │
│     运营仪表盘 · 人工介入 · 异常归因 · 配置变更管理                 │
│     运行数据 + 异常归因 + 配置变更记录 ──→ 反哺 ① 知识容器          │
└─────────────────────────────────────────────────────────────────┘
```

四件套不是线性流水线，而是一个**闭环**：FlowAgent 设计方案 → Skill 提供能力 → 执行层跑起来 → 管控后台监控运维 → 运行数据反哺知识容器 → FlowAgent 下次生成更准确的方案。

## 二、四件套的关系与数据流转

### 2.1 核心数据流

| 数据流方向 | 传递什么 | 触发时机 |
|-----------|---------|---------|
| FlowAgent → 执行层 | 方案蓝图 JSON（节点 + 连线 + 人机分工 + Skill 绑定 + 初始配置） | 技术方确认方案 |
| Skill 平台 → 执行层 | 标准化的引擎模板 + I/O schema + 运行时依赖 | 方案部署时拉取 |
| 执行层 → 管控后台 | 运行状态、执行日志、异常事件、效果指标 | 实时推送 |
| 管控后台 → 知识容器 | 异常归因标注、效果评估数据、配置变更记录 | 技术方标注 / 系统自动 |
| 知识容器 → FlowAgent | 已验证方案模板、人机分工规则、业务领域知识 | AI 翻译时检索 |
| 执行层 → 知识容器 | 配置变更轨迹 + 效果关联数据 | 每次配置变更 + 效果评估 |
| Skill 平台 → 知识容器 | Skill 使用统计、性能指标、版本变更 | 定期同步 |

### 2.2 知识容器是数据中枢

知识容器不是 FlowAgent 的一个功能模块，而是**贯穿四件套的数据中枢**。四个产品都在往里写，FlowAgent 的 AI 翻译引擎从中读取。

```
                    ┌───────────────────────────┐
    FlowAgent ────→ │                           │ ←──── Skill 平台
    (方案知识)       │       知识容器              │       (能力统计)
                    │   企业业务知识图谱           │
    执行层 ────────→ │                           │ ←──── 管控后台
    (运行知识)       │                           │       (异常归因)
                    └─────────┬─────────────────┘
                              │
                              ▼
                    FlowAgent AI 翻译引擎
                    (检索参考，越用越准)
```

## 三、执行层架构

> 这是四件套中当前设计最需要补充的部分。

### 3.1 定位

自建执行层，作为产品矩阵的第三件套。不依赖外部平台（Dify/LangGraph）作为生产执行环境。

**为什么自建而不是对接外部**：

| 维度 | 对接外部 | 自建 |
|------|---------|------|
| 数据闭环 | 运行数据在外部平台，拉回来有延迟和格式损失 | 一手数据，结构化采集，实时反哺知识容器 |
| 配置外化 | 受限于外部平台的配置能力 | 完全按产品需求设计配置体系 |
| 用户体验 | 用户需要在两个平台之间切换 | 一站式体验 |
| 演进自由度 | 受限于外部平台的 API 和路线图 | 完全自主 |

### 3.2 核心设计原则：引擎 + 配置分离

每个可执行单元（Workflow 节点 / Agentic 阶段）拆成两部分：

```
┌──────────────────────────────────────────┐
│  可执行单元                                │
│                                           │
│  ┌─────────────────┐  ┌────────────────┐ │
│  │  引擎模板         │  │  外化配置       │ │
│  │  (Engine)        │  │  (Config)      │ │
│  │                  │  │                │ │
│  │  技术方开发       │  │  业务方可改     │ │
│  │  不常变           │  │  频繁变         │ │
│  │  决定"怎么跑"    │  │  决定"按什么跑" │ │
│  └─────────────────┘  └────────────────┘ │
└──────────────────────────────────────────┘
```

这是低代码平台的核心哲学：**把模块化的东西打包，用户只需要填写他们理解的必要参数。**

规则变了（比如字段 A 今年映射成 B，明年映射成 BX），改配置就行，不需要重新生成微服务。

### 3.3 Workflow 执行

Workflow 的每个节点 = 引擎模板 + 外化规则配置。

**引擎模板**（技术方开发和维护）：
- 数据清洗引擎、API 调用引擎、审批引擎、通知引擎、文件处理引擎...
- 定义执行逻辑、数据流转、异常处理框架
- 来自 Skill 平台的标准化能力

**外化规则配置**（业务方可改）：

| 配置类型 | 举例 | 变更频率 |
|----------|------|---------|
| 字段映射 | A 字段在 AX 条件下 → B | 业务规则变更时 |
| 校验条件 | 金额 > 0，日期格式 YYYY-MM-DD | 合规要求更新时 |
| 阈值参数 | 批量大小 1000，超时 30s | 性能调优时 |
| 异常处理策略 | 校验失败 → 标记跳过 / 中断 / 人工处理 | 运营经验积累时 |
| 路由规则 | 金额 > 5000 → 主管审批，否则自动通过 | 审批策略调整时 |

**配置变更 → 立即生效**，不需要重新部署微服务。业务方在管控后台看到的是一张表单，不是代码。

### 3.4 Agentic 执行

Agentic 的每个阶段 = Agent 运行时 + 外化策略配置。

与 Workflow 的关键区别：Workflow 的配置是**确定性规则**（改了映射就是改了），Agentic 的配置是**策略方向**（改了风格，AI 不一定 100% 遵守，效果需要观察期）。

**外化策略配置**（业务方可改）：

| 配置类型 | 举例 | 变更频率 |
|----------|------|---------|
| 目标人群 | 25-35 女性 → 18-28 Z 世代 | 市场策略调整时 |
| 内容风格 | 专业严谨 → 轻松活泼 | 品牌调性变化时 |
| 发布频率 | 每天 3 条 → 每天 5 条 | 运营节奏变化时 |
| 评估标准 | 互动率 > 3% → 互动率 > 5% | KPI 调整时 |
| 敏感词库 | v1 → v2 | 合规要求更新时 |
| 降级方案 | AI 生成失败 → 用模板库兜底 | 运营经验积累时 |

**策略变更 → Agent 下次执行时遵守 → 效果需要观察期。** 这意味着 Agentic 的配置变更比 Workflow 更需要追踪和评估。

### 3.5 配置变更追踪

每次配置变更，系统自动记录：

```
变更记录 #47
  时间：2026-05-15 14:30
  操作人：张三（业务方）
  变更内容：目标人群 "25-35 女性" → "18-28 Z世代"
  关联方案：小红书矩阵运营 v3
  关联阶段：阶段一 · 账号养成
  变更原因：Q3 市场策略调整（可选填写）
```

当效果数据回来后，系统自动关联：

```
变更记录 #47 的效果评估
  变更前（5.1-5.15）：互动率 3.2%，涨粉 +120/天
  变更后（5.15-5.30）：互动率 5.8%，涨粉 +340/天
  结论：有效 ↑
```

**"配置 x 效果"的关联数据，是企业最有价值的运营知识。** AI 积累够了之后，可以主动建议："根据历史数据，这个品类每天 4 条是最优发布频率，不建议再加。"

### 3.6 远期愿景：AI 自动生成微服务

类似 Claude Code 的能力——方案确认后，AI 自动为每个节点生成实现代码，部署为可运行的微服务。

```
方案确认
  ↓
AI 为每个节点生成引擎代码 + 默认配置
  ↓
在沙箱中试运行（Mock 数据）
  ↓
用户体验流程效果
  ↓
反馈"这里不对 / 这里要改"
  ↓
AI 修改代码 → 重新试运行
  ↓
满意后部署到生产
  ↓
运行结果自动反哺知识容器
```

这是最终形态，需要 AI 代码生成能力足够成熟、企业有标准化的开发框架和部署环境。分阶段推进（见第五章）。

## 四、知识容器（升级版）

> 现有设计聚焦于"方案知识"，升级后覆盖三层。

### 4.1 从方案知识库到企业业务知识图谱

知识容器不只是存"方案怎么设计"，而是存企业在自动化过程中产生的**所有结构化知识**。

**三层架构**：

```
┌─────────────────────────────────────────────────────┐
│  第三层：运行知识（上层）                               │
│  执行日志 · 配置变更轨迹 · 效果关联 · 异常归因           │
│  来源：执行层 + 管控后台                                │
│  特点：自动采集，实时更新                               │
├─────────────────────────────────────────────────────┤
│  第二层：方案知识（中层）                               │
│  已验证方案模板 · 修正记录 · 人机分工规则                 │
│  来源：FlowAgent（方案确认时自动沉淀）                   │
│  特点：每次确认方案就是一次知识沉淀                       │
├─────────────────────────────────────────────────────┤
│  第一层：业务领域知识（底层）                            │
│  行业规则 · 企业约束 · 数据关系 · SOP · API 文档         │
│  来源：人工录入 + SOP 文档提取 + Skill 平台              │
│  特点：不绑定任何方案，是所有方案的公共基础                │
└─────────────────────────────────────────────────────┘
```

### 4.2 为什么需要三层

现有设计只覆盖第二层（方案知识），导致两个缺口：

**缺口一：业务本身的知识无处安放**

企业的知识不只是"退款流程怎么走"，还包括：
- 不同国家的退款政策差异（美国 30 天、欧盟 14 天、日本 8 天）
- 不同品类的退货率基准（服装 25%、电子 8%）
- 各平台的 API 限制和规则变更历史
- 供应商的交付周期和可靠性评级

这些知识不属于任何一个方案，但会影响所有方案的生成质量。→ 第一层解决。

**缺口二：运行效果和配置变更没有结构化沉淀**

"目标人群从 25-35 改成 18-28 后互动率从 3.2% 涨到 5.8%"——这种"配置 x 效果"的关联数据，是企业最有价值的运营知识，但现有设计里没有位置存。→ 第三层解决。

### 4.3 知识在四件套之间的流动

| 产品 | 写入什么知识 | 读取什么知识 |
|------|------------|------------|
| **FlowAgent** | 方案骨架、关键决策、AI 初版 vs 终版 Diff | 全部三层（AI 翻译时检索参考） |
| **Skill 平台** | Skill 使用统计、性能指标、版本变更 | 第一层（API 文档、接口约束） |
| **执行层** | 执行日志、配置变更轨迹、效果指标 | 第一层 + 第二层（运行时参考方案配置和业务规则） |
| **管控后台** | 异常归因标注、效果评估数据 | 第三层（展示运行知识给运维人员） |

### 4.4 自进化飞轮

三层知识驱动 AI 持续进化：

**第一层进化：记忆** — 记住用户改了什么，下次不犯同样的错。

**第二层进化：归纳** — 从多次修正中提炼通用规则（"涉及资金操作的步骤默认人工执行"），写回 AI prompt。

**第三层进化：判断** — 从"被动回答"到"主动质疑"（"你说要全自动处理退款，但根据过往案例，超过 5000 元的退款都需要主管审批，你确定要全自动吗？"）。

**飞轮效应**：用得越多 → 知识越丰富 → AI 越准 → 技术方审核越轻松 → 用得更多。这是竞品抄不走的壁垒，因为知识是企业私有的。

## 五、演进路径

### 三阶段与四件套的对应

```
          FlowAgent    Skill平台    执行层       管控后台     知识容器
          ─────────    ─────────    ──────       ────────     ────────
阶段一     ✅ Demo      ─            ─            ✅ Mock      第二层雏形
(当前)     方案设计                                仪表盘       方案知识
           双角色协作                              Mock 数据

阶段二     ✅ 完善      规划接口      基础版        真实数据     第一层+第二层
(1-3月)    知识参考      I/O schema   试运行        异常归因     + 第三层基础
           AI 验证模式   Skill 检索   配置外化      人工介入     知识飞轮启动

阶段三     ✅ 成熟      ✅ 上线      生产版        智能管控     三层完整
(3-6月)    业务方自助    Skill 市场   AI 生成微服务  主动检测     自进化成熟
           模板市场      社区生态     全链路执行     配置变更管理
```

### 阶段一 → 阶段二的关键跳板

**知识积累**。当已确认方案达到一定数量后，AI 生成质量显著提升，业务方可以从"旁观者"变为"参与者"。

### 阶段二 → 阶段三的关键跳板

**Skill 标准化**。当 Skill 平台的 I/O schema 足够完善时，FlowAgent 可以直接输出可执行的 Flow，而不仅仅是"参考蓝图"。

### 各阶段的用户体验变化

| 阶段 | 业务方体验 | 技术方体验 |
|------|-----------|-----------|
| **一** | 口述需求，技术方代操作 | 在 FlowAgent 上生成 + 修正方案，确认后参考蓝图搭建 |
| **二** | 自己输入需求，看到方案后提反馈，试运行体验效果 | 快速审核（大部分决策已被知识覆盖），标注异常归因 |
| **三** | 常见场景直接匹配模板，改配置就能用，异常时才找技术方 | 维护引擎模板和 Skill，处理复杂异常，优化知识规则 |

## 六、与竞品的本质区别

### 6.1 不是同一个赛道

市面上的产品都在解决链路上的**某一段**：

| 产品类型 | 代表 | 解决什么 | 不解决什么 |
|----------|------|---------|-----------|
| AI Agent 开发平台 | Dify, Coze, CrewAI | 怎么搭建和运行 Agent | 业务需求怎么翻译成方案 |
| 工作流自动化 | n8n, Zapier, Make | 怎么连接系统和自动化 | 业务方和技术方怎么协作 |
| 流程图工具 | BPMNCHAT, LucidFlow | 怎么画流程图 | 画完之后怎么执行和沉淀 |

我们做的是**全链路**：

```
业务方的想法
    ↓ ① FlowAgent 翻译
结构化方案蓝图
    ↓ ② Skill 平台提供能力
可执行的自动化流程
    ↓ ③ 执行层运行
真实的业务效果
    ↓ ④ 管控后台监控
运行数据和异常
    ↓ 反哺知识容器
下次翻译更准确
```

### 6.2 核心壁垒

**短期壁垒**：双角色协作设计（业务方 + 技术方在同一平台上）。市面上没有产品这么做，因为它们都假设一个人搞定。

**长期壁垒**：知识容器。每次使用都在沉淀企业私有的结构化业务知识。竞品的知识库是手动上传的静态文档；我们的知识是从使用中自然生长的、经过验证的、和执行效果关联的活数据。

**终极壁垒**：配置 x 效果的关联数据。当企业在平台上积累了"什么配置在什么场景下效果最好"的数据后，这些数据本身就是无法迁移的资产。
