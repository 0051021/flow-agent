Runtime Pack 协议规范

平台与 Agent Runtime 之间的完整数据合约 — 定义输入、执行约束、校验规则和输出格式。

协议定位
Runtime Pack 是平台打包给 Agent Runtime（如 OpenClaw）的一个自包含文件夹。Agent 打开这个文件夹，就拥有执行一个 Task 所需的全部信息——指令、数据、能力、约束、校验规则。Agent 执行完毕后，在同一文件夹内写入 output.json 返回结果。

文件结构

runtime-pack/ ├── execution-envelope.json ← 主合约：指令 + 约束 + 校验规则 ├── context.json ← 运行时上下文：业务输入 + 上游输出 + 配置 ├── skills/ │ ├── sds-reader/ │ │ ├── SKILL.md ← 自然语言能力说明 │ │ └── skill.yaml ← 结构化元数据（触发条件、依赖、输出） │ └── regulation-lookup/ │ ├── SKILL.md │ └── skill.yaml ├── tools/ │ └── platform-tools.json ← 平台提供的工具声明 ├── mcp.json ← MCP Server 配置 ├── validators/ ← 校验脚本（平台执行，非 Agent） │ ├── verify-parse-run.sh │ └── verify-record-count.py └── output.json ← Agent 输出 + 平台回填校验结果
自包含原则
Runtime Pack 不依赖外部文件。所有 JSON Schema 必须内联（不使用外部 $ref），所有 Skill 定义自包含，所有校验脚本打包在 validators/ 内。

五层架构

协议按 Agent 执行的五个阶段组织，每一层由特定文件和字段支撑：

🧠
L1 理解层
Agent 开机后理解「我要做什么、有什么数据、做到什么程度」

协议来源：execution-envelope.json → task.* + context.json + skills/*/SKILL.md

🗂
L2 规划层
Agent 判断用哪些 Skill、什么顺序、有什么依赖

协议来源：skills/*/skill.yaml（trigger_when, requires, provides）

Workflow Task 不需要此层——平台 flow 已编排好，Agent 直接执行。
Agentic Task 必须有此层——Agent 根据输入内容自主规划 Skill 使用路径。

⚡
L3 执行层
Agent 调用工具、处理数据、遇到歧义时请求人工介入

协议来源：tools/platform-tools.json + mcp.json + policies.interaction

🛡
L4 校验层
用确定性规则（非 AI）校验输出，包括字段校验、逻辑校验、脚本校验

协议来源：policies.validation_rules + validators/

由平台执行，不由 Agent 执行——确保校验不可绕过。

📊
L5 反馈层
Agent 报告结果、质量信息、执行轨迹；平台回填校验结果

协议来源：output.json（result + quality + trace）

execution-envelope.json

平台传递给 Agent 的主合约文件，包含任务定义、执行约束和校验规则。

JSON
{
  "protocol_version": "1.0",
  "runtime_run_id": "run-20260511-001",
  "job_run_id": "job-20260511-gsds-batch-05",

  // ── L1 理解层 ──
  "task": {
    "code": "compliance-review",
    "name": "合规文档审查",
    "type": "agentic",
    "instruction": "审查产品技术文档是否符合目标市场法规要求...",
    "skill_codes": ["sds-reader", "regulation-lookup", "gap-analyzer", "report-writer"],
    "output_schema": {
      "type": "object",
      "required": ["conclusion", "passed_items", "failed_items"],
      "properties": { /* 完整 JSON Schema，内联不引用外部文件 */ }
    }
  },

  // ── L3 执行层 ──
  "policies": {
    "timeout_seconds": 600,
    "max_tool_calls": 50,
    "max_tokens": 100000,

    "interaction": {
      "enabled": true,
      "endpoint": "/api/interactions/{runtime_run_id}",
      "question_policy": {
        "max_questions": 5,
        "timeout_seconds": 3600,
        "on_timeout": "use_default_and_continue"
      },
      "notify": {
        "channels": ["feishu"],
        "roles": ["compliance_reviewer"],
        "escalation": {
          "after_minutes": 30,
          "to_roles": ["compliance_manager"]
        }
      }
    },

    "degradation": {
      "on_tool_failure": "retry_once_then_skip",
      "on_skill_failure": "report_partial_result",
      "on_timeout": "return_partial_with_warning"
    },

    // ── L4 校验层 ──
    "validation_rules": [
      /* 详见「三类校验机制」章节 */
    ]
  }
}

字段说明

字段层级状态说明
protocol_version—已有协议格式版本号，用于跨版本兼容。当前固定 "1.0"
runtime_run_id—已有本次 Task 执行的唯一 ID
job_run_id—已有所属 Job 运行 ID，用于关联同批次多个 Task
task.codeL1已有Task 标识符，对应 JobSpec 中的 task code
task.nameL1已有人类可读的 Task 名称
task.typeL1已有agentic / integration / deterministic / human_review
task.instructionL1已有自然语言指令，描述 Agent 要完成的工作
task.skill_codesL1已有可用 Skill 列表（Workflow 通常 1 个，Agentic 多个）
task.output_schemaL1已有输出的 JSON Schema，必须内联完整定义
policies.timeout_secondsL3已有总执行超时
policies.max_tool_callsL3新增工具调用次数上限，防止死循环
policies.max_tokensL3新增LLM Token 消耗上限
policies.interactionL3新增人机交互完整配置（见交互通道）
policies.degradationL3新增降级策略（见降级策略）
policies.validation_rulesL4新增校验规则列表（见三类校验）
task.review_configL1新增human_review 独有：审核界面、可编辑字段、超时策略、通知（见human_review）

context.json

运行时上下文：业务输入数据、上游节点输出、配置参数。

JSON
{
  // 本次要处理的业务数据（每次执行不同）
  "context_package": {
    "product_id": "X-2026",
    "target_market": "EU",
    "sds_file_path": "/inputs/product-x-2026-sds.pdf"
  },

  // 上游节点的输出（Workflow 场景下由平台注入）
  "upstream_outputs": {
    "node-1": {
      "status": "succeeded",
      "result": {
        "downloaded_files": ["/inputs/product-x-2026-sds.pdf"]
      }
    }
  },

  // 配置项（通常跨批次不变）
  "configuration": {
    "conversion_rules_path": "/inputs/imi_conversion_rules.xlsx",
    "strict_mode": true
  }
}
字段状态说明
context_package已有业务输入数据，每次执行不同
upstream_outputs已有上游节点输出，Workflow 场景由平台按 flow 注入
configuration新增与 context_package 分离的配置项（规则文件、开关等），通常跨批次不变
为什么拆分 configuration
context_package 是「这一次要处理什么」，configuration 是「按什么规则处理」。分离后 Agent 能更快定位重点，配置变更和数据变更也能独立管理。

skills/ 目录

每个 Skill 包含两个文件：SKILL.md（自然语言）和 skill.yaml（结构化元数据）。

SKILL.md — 给 Agent 的自然语言说明

MARKDOWN
# SDS 文档读取器 (sds-reader)

## 能力
解析 SDS (Safety Data Sheet) PDF 文档，
提取结构化字段：产品名、CAS 号、成分表、危险分类、GHS 标签等。

## 什么时候用
- 任务涉及产品安全数据文档时，作为第一步使用
- 支持格式：PDF、DOCX

## 输入
- 文件路径（从 context_package 或上游节点获取）

## 输出
- structured_sds: 结构化的 SDS 数据对象

## 使用的工具
- pdf-reader（平台 Tool）

## 注意
- 如果 PDF 是扫描件，OCR 识别率可能较低，confidence 会下降
- 如果必填字段缺失，在输出中标注 missing 而不是猜测

skill.yaml — 结构化元数据 新增

YAML
code: sds-reader
version: "1.0"

# ── 什么时候该用这个 Skill ──
trigger_when:
  description: "任务输入包含 SDS/安全数据表文件"
  input_contains:
    - field: "sds_file_path"
    - field: "*.sds.*"

# ── 这个 Skill 能产出什么 ──
provides:
  - field: structured_sds
    type: object
    description: "结构化的 SDS 数据"

# ── 依赖什么输入 / 其他 Skill ──
requires:
  inputs:
    - field: file_path
      source: "context_package.sds_file_path 或 upstream_outputs"
  skills: []      # 无前置 Skill 依赖

# ── 使用的工具 ──
tools:
  - pdf-reader

# ── 约束 ──
constraints:
  max_file_size_mb: 50
  supported_formats: ["pdf", "docx"]
skill.yaml 的作用
Workflow Task 不依赖 skill.yaml——平台已通过 flow 决定用哪个 Skill，Agent 直接执行。
Agentic Task 必须有 skill.yaml——Agent 需要读 trigger_when 判断该不该用、读 requires.skills 排依赖顺序。

Skill 依赖图示例

sds-reader ─────────┐ ├──→ gap-analyzer ──→ report-writer regulation-lookup ──┘ Agent 通过 skill.yaml 中的 requires.skills 自动推导此依赖图

Secret 引用
MCP 配置中的敏感信息使用 ${SECRET:key} 语法引用，平台在打包 Runtime Pack 时注入真实值。Skill 和 Agent 不直接接触凭据原文。

validators/ 目录 新增

存放 L4 校验层使用的可执行脚本。这些脚本由平台在 Agent 输出后执行，不由 Agent 执行。

三类校验机制

类型说明执行者示例
schema 字段级 JSON Schema 校验 平台（自动） conclusion 必须是 pass/conditional_pass/fail
logic 跨字段条件表达式 平台（自动） 如果 conclusion == fail，则 failed_items 不能为空
script 可执行脚本，支持调 API / 查数据库 平台（执行脚本） 调用解析服务 API 确认 run_id 真实执行过 
JSON — validation_rules 示例
[
  {
    "id": "v-001",
    "type": "schema",
    "field": "conclusion",
    "rule": "in_enum",
    "values": ["pass", "conditional_pass", "fail"],
    "severity": "error",
    "message": "结论必须是 pass/conditional_pass/fail 之一"
  },
  {
    "id": "v-002",
    "type": "logic",
    "condition": "result.conclusion == 'fail' && result.failed_items.length > 0",
    "severity": "error",
    "message": "结论为 fail 时必须列出不通过项"
  },
  {
    "id": "v-010",
    "type": "script",
    "script": "validators/verify-parse-run.sh",
    "description": "验证解析接口是否真实执行过",
    "input_mapping": {
      "PARSE_RUN_ID": "result.parse_run_id"
    },
    "expected_exit_code": 0,
    "timeout_seconds": 30,
    "severity": "error"
  }
]
设计原则：考试不能让考生自己改卷
校验的目的是不信任 Agent，所以校验必须由平台执行。validation_rules 写在 execution-envelope.json 里给平台看，Agent 不需要感知校验规则的存在——它只管按 output_schema 输出结果。

脚本合约

约定说明
输入通过 input_mapping 将 output.json 中的字段映射为环境变量
输出stdout 输出 JSON 对象 {"passed": bool, "detail": "..."}
退出码0 = 通过，非 0 = 失败
超时由 timeout_seconds 控制，超时视为失败
语言不限（Shell / Python / Node 等），需在 runtime-pack 中自包含依赖

人机交互通道

Agentic Task 执行过程中可能遇到歧义，需要人工确认。协议定义了完整的交互策略。

JSON — policies.interaction
{
  "enabled": true,
  "endpoint": "/api/interactions/{runtime_run_id}",

  "question_policy": {
    "max_questions": 5,           // 最多问 5 次
    "timeout_seconds": 3600,      // 等人回复最长 1 小时
    "on_timeout": "use_default_and_continue"
                                    // 超时后使用默认值继续，不阻塞
  },

  "notify": {
    "channels": ["feishu"],      // 通知渠道：飞书/钉钉/邮件
    "roles": ["reviewer"],       // 通知对象角色
    "escalation": {
      "after_minutes": 30,       // 30 分钟无人回复则升级
      "to_roles": ["manager"]   // 升级通知对象
    }
  }
}
异步推送模式
Agent 提出问题后不要求人盯着进度。平台通过飞书/钉钉等渠道推送通知，人在消息内直接回复，平台将回复转发给 Agent。超时未回复则按降级策略处理。

降级策略

场景策略选项说明
工具调用失败 retry_once_then_skip
retry_and_fail
skip_silently 		重试一次后跳过 / 重试后失败 / 直接跳过
Skill 执行失败 report_partial_result
fail_task 		报告部分结果继续 / 整个 Task 标记失败
超时 return_partial_with_warning
fail_task 		返回已完成部分并附警告 / 标记失败
人工回复超时 use_default_and_continue
pause_and_wait
fail_task 		用默认值继续 / 暂停等待 / 失败

human_review 任务

human_review 和 Agentic 的「偶尔问人」完全不同——这个 Task 的整个执行者就是人，不经过 Agent Runtime。

关键区别
Agentic + interaction：AI 在执行，遇到歧义时问人一个问题，人回答后 AI 继续。AI 是主体。
human_review：平台把数据展示给人，人审核/修改后提交。人是主体，没有 AI 参与执行。

执行流程

平台接收到 human_review 类型 Task ↓ 不发给 Agent Runtime，而是： ↓ ┌─────────────────────────────────────────┐ │ 1. 根据 review_config.notify 推送通知 │ │ → 飞书/钉钉/邮件通知审核人 │ │ │ │ 2. 审核人打开平台 UI │ │ → 展示 input 数据（上游节点输出） │ │ → 根据 review_config.ui 渲染表单 │ │ │ │ 3. 审核人修改/确认数据 │ │ → 可编辑字段由 editable_fields 控制 │ │ │ │ 4. 提交 │ │ → 平台写 output.json │ │ → 记录 who / when / 改了什么 │ └─────────────────────────────────────────┘ ↓ 触发下游 Task

execution-envelope.json 扩展字段

JSON
{
  "protocol_version": "1.0",
  "runtime_run_id": "run-20260511-node3-001",
  "job_run_id": "job-20260511-gsds-batch-05",

  "task": {
    "code": "node-3",
    "name": "人工审核解析结果",
    "type": "human_review",
    "instruction": "审核 PDF 解析结果的准确性，修正错误字段后确认提交。",

    // input_schema: 告诉平台输入数据的结构，用于渲染展示
    "input_schema": {
      "type": "object",
      "properties": {
        "parsed_record": { /* 上游 node-2 的输出 schema */ },
        "source_pdf_url": { "type": "string", "description": "原始 PDF 链接，供审核人对照" }
      }
    },

    // output_schema: 审核人提交后的数据结构
    "output_schema": {
      "type": "object",
      "required": ["bbn", "part"],
      "properties": {
        "bbn":  { "type": "string" },
        "part": { "type": "string" },
        "color": { "type": "string" },
        "cas_no": { "type": "string" }
      }
    },

    // ── human_review 独有配置 ──
    "review_config": {

      // 可编辑字段（其余只读展示）
      "editable_fields": ["*"],
      // 可以是 ["*"]（全部可编辑）或 ["color", "cas_no"]（指定字段）

      // 审核超时
      "timeout_seconds": 86400,
      "on_timeout": "auto_approve",
      // auto_approve: 超时自动通过（数据不变）
      // escalate: 超时升级给上级

字段说明

字段位置状态说明
review_configenvelope新增human_review 类型独有的顶级配置
review_config.editable_fieldsenvelope新增审核人可编辑的字段列表，["*"] 表示全部
review_config.timeout_secondsenvelope新增审核超时时间（通常远大于 Agent 超时，如 24h）
review_config.on_timeoutenvelope新增auto_approve / escalate / fail_task
review_config.notifyenvelope新增通知渠道、提醒间隔、升级机制
review_config.uienvelope新增审核界面布局提示（左右对照 / 纯表单 / 差异视图）
review_config.ui.highlight_low_confidenceenvelope新增标黄上游 Agent 低置信度字段，引导审核人重点关注
review_auditoutput新增审核轨迹：谁审的、什么时候、改了哪些字段
review_audit.changesoutput新增逐字段变更记录（old_value → new_value），用于审计
review_audit.notification_logoutput新增通知发送记录，便于排查「通知到了没人看」的问题
与 Agentic interaction 的本质区别

Agentic + interaction

  • AI 是执行者，人是顾问
  • AI 主动提问，人被动回答
  • 交互次数少（max_questions: 5）
  • 人回答后 AI 继续执行
  • output.json 由 Agent 写

human_review

  • 人是执行者，AI 不参与
  • 平台展示数据，人主动审核
  • 人可以修改任意可编辑字段
  • 人提交即完成，没有后续 AI 处理
  • output.json 由平台写

四类 Task 对比

协议是同一套，四种 Task 类型的区别在于谁执行、哪些字段有值、哪些层谁承担：

维度Workflow TaskAgentic Taskhuman_review Taskintegration Task
执行者 Agent Runtime Agent Runtime 人（平台 UI） 集成引擎（非 Agent）
典型场景 SOP 单步：PDF 解析 专家判断：合规审查 数据审核、审批确认 调 API、写数据库
skill_codes 1 个 多个（能力池） 无 1 个
规划层（L2） 平台 flow Agent 自主规划 不适用 不适用
interaction 通常 false 通常 true 不适用（整个 Task 就是交互） false
review_config 无 无 必须 无
validation_rules 严格 严格 + 兜底 表单实时校验 严格
confidence 高（确定性） 有高有低 1.0（人确认） 1.0（确定性）
trace 1 步 多步 不适用（用 review_audit 替代） API 调用记录
output.json 由谁写 Agent Agent 平台 集成引擎
一套协议，四种姿态
不需要维护四套协议。同一个 execution-envelope.json 结构，根据 task.type 决定哪些字段生效：
agentic → 填 skill_codes + interaction + degradation
human_review → 填 review_config（不需要 skill_codes、interaction、degradation）
integration → 填 skill_codes + tool_codes（不需要 interaction）
复杂度跟着业务走，而不是跟着协议走。
