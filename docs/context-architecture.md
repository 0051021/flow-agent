## 一、核心理念

### 1.1 以上下文为中心，而非以 Agent 为中心

传统 Agent 架构的思考方式：

```
Agent 有什么工具？
Agent 的 prompt 怎么写？
Agent 怎么调用 Skill？
Agent 怎么和另一个 Agent 协作？
```

这是**以 Agent 为中心**的思维。它关注"谁在做事"，但忽略了"什么在流动"。

FlowAgent 体系采用**以上下文为中心**的架构：

```
传统软件架构问：组件有哪些？它们怎么通信？
Agent 架构问：   上下文在哪里？它怎么流动？谁在变换它？
```

Agent 不是主角。**上下文才是主角。** Agent 只是上下文的处理器——读入一段上下文，做决策，输出新的上下文。FlowAgent 的整个产品，本质上是在管理**业务上下文从意图到落地到学习的完整生命周期**。

### 1.2 FlowAgent 四件套的上下文角色

| 产品模块 | 上下文架构中的角色 | 操作的上下文层级 |
|---------|------------------|----------------|
| **FlowAgent 编辑器** | 上下文结构设计器 | L3-L4（定义任务和项目的上下文结构） |
| **Skill 平台** | 上下文处理器注册中心 | L1（每个 Skill 是一个 L1 上下文变换器） |
| **执行引擎** | 上下文运行时 | L1-L2（执行步骤，管理执行状态） |
| **管控后台** | 上下文观测与干预界面 | L2-L4（监控进度，处理异常，调整策略） |
| **知识层 (Gene)** | 上下文压缩存储 | L5-L6（长期知识，跨项目复用） |

```
上下文的生命周期：

   创建              变换                压缩
   ┌──────┐         ┌──────┐           ┌──────┐
   │构造上下│         │处理上下│           │蒸馏上下│
   │文结构  │   →     │文实例  │    →      │文为知识│
   └──┬───┘         └──┬───┘           └──┬───┘
      │                │                  │
      ▼                ▼                  ▼
   FlowAgent         执行引擎            知识层
   编辑器            + Skill 平台         (Gene 池)

   "定义上下文        "运行上下文          "把上下文经验
    应该长什么样"      通过处理器"          压缩为可复用知识"

                    管控后台
                    "人类观察和干预
                     上下文流动"
```

## 二、六层上下文模型

上下文不等于 LLM 的 prompt。在一个真实的多任务 Agent 系统里，上下文有六个层级，每一层的生命周期、作用域、消费者完全不同：

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  Layer 6 · 组织上下文                          生命周期：年级  │
│  ─────────────────                                           │
│  企业是做什么的、什么行业、什么文化、什么底线                     │
│  "我们是跨境电商公司，合规是底线，数据安全第一"                   │
│                                                              │
│  Layer 5 · 领域上下文                          生命周期：月级  │
│  ─────────────────                                           │
│  行业知识、平台规则、Gene 池、已验证的模式                       │
│  "小红书美食类内容 CTR 基线 8%"                                │
│  "报关场景必须校验 HS 编码位数"                                 │
│                                                              │
│  Layer 4 · 项目上下文                        生命周期：周/月级 │
│  ─────────────────                                           │
│  项目目标、任务分解、跨任务依赖、资源约束、环境假设              │
│  "小红书运营项目，3 个 Task，预算 5000/月"                      │
│  "假设：美食类 CTR ≥ 8%"                                      │
│                                                              │
│  Layer 3 · 任务上下文                        生命周期：天/周级 │
│  ─────────────────                                           │
│  当前 Task 的目标、策略、约束、进度、人机分工                    │
│  "内容创作 Task，美食 70%，本周发了 8 篇"                       │
│                                                              │
│  Layer 2 · 执行上下文                        生命周期：小时级  │
│  ─────────────────                                           │
│  当前这一轮执行的状态、中间结果、决策轨迹                        │
│  "正在生成第 9 篇内容，主题是春季甜品"                          │
│                                                              │
│  Layer 1 · 步骤上下文                        生命周期：秒/分级 │
│  ─────────────────                                           │
│  当前这一步的输入、输出、Skill 调用参数                          │
│  "调用内容生成 Skill，输入：主题=春季甜品，风格=活泼"            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 层级与 FlowAgent 产品概念的映射

| 层级 | 对应的产品概念 | 谁写入 | 谁读取 |
|------|-------------|--------|--------|
| L6 组织 | 企业知识库（通用文件） | 管理员（手动） | AI 翻译（始终注入通用 Gene） |
| L5 领域 | Gene 池 + 方案模板 | 自进化飞轮（自动蒸馏） | AI 翻译（匹配注入） |
| L4 项目 | Project 配置 | FlowAgent 编辑器（设计时） | 管控后台（运行时监控） |
| L3 任务 | Scheme + SchemeVersion | FlowAgent 编辑器 + 管控后台（策略调整） | 执行引擎（任务目标和约束） |
| L2 执行 | Execution 实例 | 执行引擎（自动） | 管控后台（进度监控） |
| L1 步骤 | Skill 调用记录 | 执行引擎（自动） | 三层评估（工具级评估） |

### 2.2 上下文注入：每个决策点该看到什么

Agent 做决策时，LLM 的上下文窗口是有限的。核心问题不是"有什么信息"，而是**在这个决策点，应该注入哪几层的哪些片段**。

```
Agent 做一个步骤决策时，上下文窗口里应该有：

必须有的（always inject）：
  L1 · 这一步的输入数据 + Skill 的 schema
  L3 · 当前 Task 的目标和约束（精简版）

按需注入的（match & inject）：
  L5 · 匹配到的 Gene（≤ 500 token）
  L2 · 前面几步的关键输出（摘要，不是全部）
  L4 · 相关的跨 Task 依赖说明（如果有上游 Task）

不应该有的（exclude）：
  L4 · 项目级的其他 Task 详情（和这一步无关，浪费 token）
  L6 · 企业完整制度文档（太长，用 Gene 替代）
```

Gene 机制本质上就是对 L5-L6 的**高密度压缩**——让 200 token 携带了 2500 token 文档的控制信息。

## 三、上下文的三个流动方向

### 3.1 向下约束（设计时 → 运行时）

高层上下文逐层分解为低层约束：

```
L6 组织上下文："合规是底线"
    ↓
L4 项目上下文："所有内容必须合规审查"
    ↓
L3 任务上下文："内容创作 Task 必须经过合规 Skill"
    ↓
L1 步骤上下文："调用内容生成 Skill 时注入合规约束参数"
```

**FlowAgent 编辑器的核心工作就是向下约束**——把业务意图逐层分解为可执行的结构化上下文。方案蓝图本质是一份"上下文向下传导的规则书"。

### 3.2 向上反馈（运行时 → 知识层）

低层执行结果沿层级向上聚合，最终蒸馏为长期知识：

```
L1 步骤结果："这篇内容被平台标记低质量"
    ↑ 聚合
L2 执行结果："本轮 30 篇，5 篇被标记低质量"
    ↑ 聚合
L3 任务进度："内容合格率 83%，低于 95% 目标"
    ↑ 聚合
L4 项目状态："内容质量问题影响粉丝增长"
    ↑ 蒸馏
L5 Gene："内容生成时避免使用 XX 类表述，平台会判定低质量"
```

### 3.3 横向传递（Agent 之间 / Task 之间）

同层级的上下文在 Task/Agent 之间传递：

```
Task A（选品调研）输出：
  "目标人群偏好：25-35 岁女性，关注健康饮食"
    → 传递给 →
Task B（内容创作）输入：
  "目标受众：25-35 岁女性，内容方向：健康饮食"
```

横向传递的关键不是"传了什么数据"，而是"传递时保留了多少上下文质量信号"。级联失败（`flowagent-product.md` 3.2.5.1）就发生在这里——数据完整但质量维度丢失。

## 四、Context Package：上下文交接契约

### 4.1 问题

传统的节点交接只传数据：

```
Skill A 输出 → { data } → Skill B 输入
```

这导致质量信号丢失。Skill A 输出的 HS 编码精度只有 6 位，但 Skill B 看不到这个信息，只看到"有一个 HS 编码字段"。

### 4.2 Context Package 结构

每次上下文交接都通过标准化的 Context Package 进行：

```
Context Package = {
  // 核心数据
  data: {
    hs_code: "8471.30",
    amount: 50000,
    currency: "CNY",
    ...
  },

  // 质量信号（关键！）
  quality_signals: {
    confidence: 0.85,
    hs_code_precision: 6,         // 精度信号
    field_completeness: 0.95,      // 字段完整率
    known_limitations: [
      "HS 编码仅 6 位，可能不够精确",
      "外币金额未做汇率转换"
    ]
  },

  // 环境假设
  assumptions: [
    "基于 2026 年关税税率表",
    "汇率按 4 月 1 日中间价"
  ],

  // 决策轨迹（归因用）
  trace: {
    key_decisions: ["使用 OCR 引擎 v3 提取"],
    alternatives_considered: ["曾考虑手动模板匹配，因准确率低放弃"],
    processing_time_ms: 1200
  }
}
```

### 4.3 质量传导层

在节点交接时增加一个**质量传导层**，自动校验 Context Package 是否满足下游要求：

```
Skill A 输出 Context Package
    ↓
质量传导层检查：
    ├─ 下游声明的最低要求：hs_code_precision ≥ 10
    ├─ 实际值：hs_code_precision = 6
    ├─ 判定：❌ 不满足
    │
    ├─ 处理策略（可配置）：
    │   ├─ strict（严格）：中断执行，告警
    │   ├─ warn（警告）：继续执行，标记风险
    │   └─ pass（透传）：忽略，让下游自己处理
    │
    └─ 当前配置：warn
        → 继续执行，在 L2 执行上下文中标记：
          "⚠️ 上游 HS 编码精度不足，可能影响合规校验结果"
```

### 4.4 质量契约的定义时机

| 任务类型 | 质量契约的定义方式 | 示例 |
|---------|------------------|------|
| **Workflow** | 设计时预定义（FlowAgent 编辑器中配置） | "单证解析 → 合规校验：hs_code_precision ≥ 10" |
| **Agentic** | 运行时逐步发现 + 复盘后固化 | 第一次跑完发现精度不够 → 复盘后补上质量契约 |

Workflow 的质量契约是"编译时"确定的，Agentic 是"运行时"逐步学习的。Agentic 的质量契约随执行经验积累，最终也会固化为组合 Gene。

## 五、Gene 维度扩展：组合 Gene

### 5.1 现有 Gene 维度

| 级别 | 作用域 | 示例 |
|------|--------|------|
| Skill Gene | 单个 Skill | "单证 OCR 不要混用扫描件和电子 PDF" |
| 场景 Gene | 某类场景 | "报关场景必须校验 HS 编码位数一致性" |
| 通用 Gene | 全局 | "涉及客户沟通的步骤默认标记人工确认" |

### 5.2 新增：组合 Gene

组合 Gene 记录的是**"A 接 B 时要注意什么"**的跨节点/跨 Task 经验：

```
{
  "type": "composition_gene",
  "upstream": "document-parsing",
  "downstream": "compliance-check",
  "keywords": ["单证解析", "合规校验", "HS编码"],
  "strategy": [
    "解析精度必须 ≥ 10 位编码，否则合规校验会产生假阳性",
    "外币金额必须在交接时声明币种，不要假设全是 CNY"
  ],
  "avoid": [
    "不要让合规校验节点自己做汇率转换，应由独立的汇率转换节点处理"
  ],
  "source": "execution_failure_distill",
  "validated_count": 5
}
```

### 5.3 组合 Gene 的来源

| 来源 | 触发条件 | 蒸馏方式 |
|------|---------|---------|
| **级联失败归因** | 归因分析发现根因在上游 | AI 自动蒸馏失败链路为 AVOID |
| **跨 Task 复盘** | 复盘发现 Task 交接质量问题 | AI 生成策略建议，技术方确认后入库 |
| **质量传导层拦截** | 质量传导层多次 warn | 统计高频 warn 模式，蒸馏为 strategy |
| **技术方手动标注** | 技术方在管控后台标注跨节点问题 | 蒸馏为 strategy/AVOID |

### 5.4 Gene 匹配注入的完整规则

AI 生成方案时，Gene 注入的匹配逻辑：

```
1. 通用 Gene → 始终注入
2. 场景 Gene → 场景标签匹配时注入
3. Skill Gene → 对应 Skill 被绑定/授权时注入
4. 组合 Gene → 两个关联节点/Task 同时出现在方案中时注入（v13 新增）

总预算 ≤ 500 token，优先级：通用 > 组合 > 场景 > Skill
```

组合 Gene 优先级高于场景和 Skill Gene，因为跨节点的失败往往比单节点失败更难发现和修复。

## 六、Workflow 与 Agentic 的上下文差异

Workflow 和 Agentic 的真正区别不是"确定 vs 灵活"，而是**上下文解析的时机不同**：

### 6.1 Workflow：上下文的"编译执行"

设计时完全解析（每步知道精确的上下文来源）：

```
设计时确定了：
  步骤 3 的输入 = 步骤 2 的输出字段 A + 步骤 1 的输出字段 B
  步骤 3 用哪个 Skill = 合规校验 v2.1
  步骤 3 的参数 = { threshold: 0.95 }

运行时只是"填值"：
  把实际数据填入已确定的结构
```

### 6.2 Agentic：上下文的"解释执行"

设计时部分解析（只确定目标和约束，路径运行时决定）：

```
设计时确定了：
  阶段 3 的目标 = "生成符合品牌调性的内容"
  阶段 3 可用的 Skill 池 = [内容生成, 图片生成, ...]
  阶段 3 的约束 = { style: "活泼", max_length: 800 }

运行时才解析：
  "根据阶段 2 的策略输出，决定生成美食类内容"
  "选择内容生成 Skill"
  "根据上文风格偏好，设置参数 { topic: '春季甜品', tone: 'casual' }"
```

### 6.3 对架构的影响

| 维度 | Workflow（编译执行） | Agentic（解释执行） |
|------|--------------------|--------------------|
| **上下文注入** | 设计时确定好的固定模板 | 运行时动态组装 |
| **失败归因** | 容易——路径确定，沿路径追溯 | 难——路径不确定，需回溯决策点 |
| **质量传导** | 可以设计时预定义契约 | 需运行时评估 + 复盘后固化 |
| **环境感知** | 弱需求（内部系统，变化少） | 强需求（外部环境，变化频繁） |
| **热更新** | 主要更新参数 | 可更新策略、Skill、甚至目标 |
| **上下文演化** | L1-L2 在运行时更新，L3+ 基本不变 | L1-L4 都可能在运行时更新 |

## 七、上下文总线（Context Bus）

### 7.1 定位

Context Bus 是贯穿 FlowAgent 四件套的统一上下文流转通道。它不是一个消息队列，而是**分层的、带生命周期管理的状态存储**。

```
┌──────┐   构造    ┌────────────┐   注入    ┌──────┐
│编辑器 │ ───────→ │            │ ───────→ │执行引 │
│      │         │  Context   │         │擎    │
│      │ ←─────── │  Bus       │ ←─────── │      │
└──────┘  模板参考  │            │  执行反馈  └──────┘
                  │  · 分层存储  │
┌──────┐  干预事件  │  · 事件路由  │  Gene注入  ┌──────┐
│管控台 │ ───────→ │  · 质量传导  │ ───────→ │知识层 │
│      │ ←─────── │  · 压缩管线  │ ←─────── │      │
└──────┘  状态查询  └────────────┘  蒸馏存储  └──────┘
```

### 7.2 Context Bus 的四个职责

**职责 1：分层存储**

每个层级的上下文有独立的存储空间和访问控制：

| 层级 | 存储特征 | 写入者 | 读取者 |
|------|---------|--------|--------|
| L6 组织 | 持久化，极少更新 | 管理员 | 所有 AI 调用 |
| L5 领域 | 持久化，自动进化 | Gene 蒸馏管线 | AI 翻译 + 执行引擎 |
| L4 项目 | 持久化，人工 + 事件更新 | 编辑器 + 管控后台 | 执行引擎 + 管控后台 |
| L3 任务 | 持久化，方案版本化 | 编辑器 + 管控后台（策略调整） | 执行引擎 |
| L2 执行 | 临时，执行完成后归档 | 执行引擎 | 管控后台 + 复盘系统 |
| L1 步骤 | 临时，高频读写 | 执行引擎 + Skill | 下一步 Skill + 评估系统 |

**职责 2：事件路由**

上下文更新时自动通知受影响的消费者：

```
L4 项目上下文更新（如预算变更）
  → 通知所有关联的 L3 任务上下文（检查约束是否还成立）
  → 通知管控后台（显示变更提醒）
  → 通知执行引擎（如果有正在运行的 Execution）

L5 Gene 池更新（新 AVOID 入库）
  → 标记受影响的已运行方案
  → 下次 AI 翻译时自动注入
```

**职责 3：质量传导**

在 L1-L2 的节点交接时执行质量契约校验（见第四章）。

**职责 4：压缩管线**

执行数据沿层级向上聚合和压缩：

```
L1 步骤结果（秒级，大量，低密度信息）
  ↓ 聚合（取关键指标、异常记录）
L2 执行摘要（小时级，每轮一个）
  ↓ 归纳（提取成功/失败模式）
L3 任务经验（天级，含模式和规律）
  ↓ 蒸馏（LLM 提炼为控制片段）
L5 Gene（月级，≤ 200 token，高密度控制信息）
```

每一级压缩做的都是："这一层发生了什么" → "下次遇到类似情况应该怎么做/避免什么"。

## 八、运行时上下文演化

上下文不是一次写入永远不变的。不同层级在运行中被不同类型的事件更新。

### 8.1 三类事件对上下文的影响

| 事件类型 | 影响的层级 | 更新方式 | 示例 |
|---------|-----------|---------|------|
| **异常事件** | L1-L2 | 自动标记异常，触发评估 | Skill 调用失败 → L1 标记错误 → L2 记录异常 |
| **环境事件** | L4-L5 | 监控检测 → 标记假设失效 → 人确认 | 平台算法变化 → L4 环境假设失效 → L5 基线更新 |
| **业务事件** | L3-L6 | 人输入 → AI 评估影响 → 分层更新 | 预算追加 → L4 资源约束更新 → L3 策略调整 |

### 8.2 环境假设监控

L4 项目上下文中的环境假设（`env_assumptions`）是重要的运行时校验点：

```
L4 项目上下文创建时（FlowAgent 编辑器）：
  env_assumptions: [
    { id: "ea-1", claim: "美食类 CTR ≥ 8%", baseline: 8.2, source: "2026-Q1" },
    { id: "ea-2", claim: "月预算 ≤ 5000", value: 5000 }
  ]

运行中（管控后台环境监控）：
  持续检查每条假设：
    ea-1: 当前美食 CTR = 5.1% → ❌ 假设失效
      → 触发环境事件
      → AI 诊断：平台级变化（整体下降）vs 自身退化
      → 推荐调整方案

    ea-2: 当前预算 = 5000 → ✅ 假设成立
```

### 8.3 业务事件的上下文穿透

业务事件（如"追加 10 万预算"）的处理链路：

```
Step 1：意图理解
  管理者输入："给小红书账号追加 10 万营销预算"
  AI 解析：资源类型=预算，数量=+100000，范围=特定账号

Step 2：影响面评估（按层级）
  L4 项目上下文 → 预算约束需更新 [直接]
  L3 任务上下文 → 策略需从纯内容转向内容+投放 [连带]
  L3 Skill 授权 → "付费投放" Skill 需要授权 [连带]
  L3 编排结构 → 可能需要增加并行路径 [连带]
  L4 目标 → 建议上调增长目标 [建议]

Step 3：分层调整方案
  🟢 Layer 1-2（立即生效）：预算更新、解锁能力授权
  🟡 Layer 3（需技术方确认）：引入新 Skill、升级现有 Skill
  🔴 Layer 4（需回编辑器）：增加付费投放并行路径

Step 4：效果验证 + 知识沉淀
  调整后持续对比效果
  蒸馏为 Gene："预算追加 10 万级别时，同步引入投放 Skill + ROI 分析"
```

## 九、对话中确认的关键设计决策

### 9.1 上下文总线的实现策略

分阶段实现，不需要一步到位：

| 阶段 | 实现方式 | 覆盖的层级 |
|------|---------|-----------|
| **Demo/Phase 1** | 前端 Zustand Store 分层管理，localStorage 持久化 | L1-L3（单方案内） |
| **Phase 2** | 服务端数据库分层存储，REST API 读写 | L1-L4（Project 级） |
| **Phase 3** | 事件驱动架构（如 Redis Streams），实时通知 | L1-L6（完整体系） |

### 9.2 质量传导层的默认策略

| 场景 | 默认策略 | 原因 |
|------|---------|------|
| Workflow 节点交接 | **warn**（警告但继续） | 已有人工确认节点兜底 |
| Agentic 阶段交接 | **warn** | Agent 有自主判断能力 |
| 涉及不可逆操作的交接 | **strict**（中断并告警） | 不可逆操作必须确保质量 |
| 灰度中的 Skill 交接 | **strict** | 新版 Skill 的输出质量未验证 |

### 9.3 组合 Gene 的 token 预算分配

总预算 500 token 不变，优先级排序：

```
通用 Gene  ≤ 100 token（始终注入）
组合 Gene  ≤ 150 token（关联节点同时出现时注入）
场景 Gene  ≤ 150 token（场景匹配时注入）
Skill Gene ≤ 100 token（Skill 匹配时注入）
```
