# Skill 平台架构设计

> 最后更新：2026-04-10
> 
> 本文档是 Skill 平台的完整架构设计，包含 Skill 的定义、切割原则、平台交互模型、标准化演进、以及与 FlowAgent / 执行层的职责边界。
>
> 产品矩阵全景见 [`product-matrix.md`](./product-matrix.md)，FlowAgent 功能设计见 [`flowagent-product.md`](./flowagent-product.md)。

---

## 一、核心问题

Skill 应该封装到什么粒度？

这个问题的答案决定了：
- FlowAgent 流程图的节点粒度
- Skill 平台的注册和管理粒度
- 执行层的调度和监控粒度
- 业务方的验收和溯源能力

---

## 二、矛盾

| 封装太厚 | 封装太薄 |
|----------|----------|
| Skill 内部包含太多步骤 | 每个 API 调用都是一个 Skill |
| 业务方看不懂里面发生了什么 | 业务方更看不懂（全是技术术语） |
| 出了问题无法溯源到具体步骤 | 流程图变成技术架构图 |
| 不利于技术方验证稳定性 | 管理成本爆炸 |

---

## 三、切割原则：以"业务可验收点"为边界

```
一个 Skill 的边界 = 从上一个"业务方能看懂并验收的输出"
                    到下一个"业务方能看懂并验收的输出"
```

### 3.1 什么是"业务可验收"

业务方能回答"到这里为止，结果对不对"这个问题。

```
✅ 业务可验收的输出：
  - "解析出来的品名是 XX、数量是 YY、金额是 ZZ" → 业务方能判断对不对
  - "合规校验结果：通过 / 不通过，原因是 XX" → 业务方能判断合不合理
  - "海关申报已提交，回执编号 XX" → 业务方能判断成功没

❌ 业务不可验收的输出：
  - "OCR 识别完成，置信度 0.95" → 业务方不知道这意味着什么
  - "规则引擎返回 JSON: {code: 200, ...}" → 业务方看不懂
  - "HTTP POST 返回 201" → 纯技术信息
```

### 3.2 切割示例：进出口报关

```
❌ 错误切法（太厚）：
  Skill "报关处理" = 解析文件 + 校验合规 + 提交海关 + 跟踪状态
  → 业务方只看到"报关处理完了"，中间出了问题完全不知道

❌ 错误切法（太薄）：
  Skill_1 "读取 PDF"
  Skill_2 "OCR 识别"
  Skill_3 "表格结构化"
  Skill_4 "字段映射"
  Skill_5 "查询关税数据库"
  Skill_6 "规则比对"
  Skill_7 "生成校验报告"
  → 业务方看不懂这些技术步骤，流程图变成了技术架构图

✅ 正确切法（以业务可验收点为界）：

  Skill "单证解析"
    内部：读取 PDF → OCR → 结构化 → 字段映射
    输出：{ 品名, 数量, 金额, HS编码, ... }
    验收点：业务方能看懂这些字段，能判断对不对

  Skill "合规校验"
    内部：查规则库 → 比对数据 → 生成报告
    输出：{ 通过/不通过, 不满足的规则列表, 建议 }
    验收点：业务方能看懂"哪条规则没过"

  Skill "海关申报"
    内部：组装报文 → 提交 → 获取回执
    输出：{ 申报状态, 回执编号 }
    验收点：业务方能看懂"提交成功了没"
```

### 3.3 Skill 的正式定义

```
Skill = 一个业务可验收的原子能力单元

特征：
  1. 输入：业务方能描述的东西（"一份报关单 PDF"）
  2. 输出：业务方能验收的东西（"结构化的单证数据"）
  3. 内部：可能包含多个技术步骤，但对外是黑盒
  4. 边界：两个相邻 Skill 之间，业务方能判断"到这里为止对不对"
```

**Skill 不是"最小技术单元"，而是"最小业务验收单元"。**

## 四、三个好处

### 4.1 溯源能力

出了问题，先定位到哪个 Skill 的输出不对，再进 Skill 内部看技术日志：

```
单证解析 ✅ → 合规校验 ❌ → 海关申报（未执行）

第一层溯源（FlowAgent / 管控后台）：
  合规校验失败

第二层溯源（Skill 平台内部日志）：
  → 规则引擎返回"HS编码不在白名单"
  → 追溯上游：单证解析输出的 HS编码是 8471.30
  → 定位：解析错了（Skill_1 的问题）还是规则库没更新（Skill_2 的问题）
```

两层溯源，第一层业务方能看懂，第二层技术方能定位。

### 4.2 业务方能参与验收

每个 Skill 的输出都是业务方能看懂的，所以人工确认节点应该放在 Skill 之间：

```
单证解析 → [人工确认：字段都对吗？] → 合规校验 → [人工确认：校验结果合理吗？] → 海关申报
```

这和 FlowAgent 的"人机分工标注"天然吻合——**人工确认节点放在 Skill 之间，不是 Skill 内部**。

### 4.3 独立验证稳定性

每个 Skill 有明确的输入/输出契约，可以独立测试：

```
Skill "单证解析" 的测试报告：
  测试数据：100 份历史单证
  准确率：98%（2 份外币单证的金额解析有误）
  平均耗时：1.2 秒
  已知问题：外币单证需要汇率转换，当前版本未支持
```

技术方交付时可以拿出每个 Skill 的测试报告，证明稳定性和正确性。

## 五、Skill 的两种形态

### 5.1 原子 Skill

内部是一个或几个紧密耦合的技术步骤，对外暴露统一的 schema。

```
Skill "单证解析 v2.1"
  输入 schema: { file: File, fileType: "pdf" | "excel" | "image" }
  输出 schema: { fields: { 品名: string, 数量: number, 金额: number, HS编码: string, ... } }
  工具级评估: 字段完整性检查 + 格式校验
```

### 5.2 Skill 编排（Skill 组合）

多个原子 Skill 串联/并联，但对外暴露的 schema 和原子 Skill 一样。

```
Skill 编排 "合规校验流程"
  内部: Skill "关税查询" → Skill "规则比对" → Skill "报告生成"
  对外 schema: { input: 单证数据, output: 校验结果 }
```

**对 FlowAgent 来说，原子 Skill 和 Skill 编排没有区别**——都是一个输入 schema + 一个输出 schema。Skill 内部是一个 API 调用还是一个 50 步的子流程，那是 Skill 平台的事。

### 5.3 Skill 的双重表达：Human Doc vs Model Gene

> 2026-04-20 新增。参考 EvoMap/清华 Gene 研究：给模型用的经验对象应按"控制密度"而非"文档完整性"设计。

每个 Skill 在知识库中有**两种表达形态**，服务不同的消费者：

**Human Doc（给人看）**：完整的 Skill 文档

```
Skill "单证解析 v2.1"
  概述：从报关单 PDF/图片中提取结构化字段
  输入 schema: { file: File, fileType: "pdf" | "excel" | "image" }
  输出 schema: { fields: { 品名, 数量, 金额, HS编码 } }
  工具级评估: 字段完整性检查 + 格式校验
  已知问题：外币单证需要汇率转换，当前版本未支持
  API 文档：https://...
  使用示例：...
  依赖关系：需要 OCR 引擎 v3+
  性能指标：准确率 98%，平均耗时 1.2s
```

**Model Gene（给模型用）**：蒸馏后的控制片段，~200 token

```
{
  "keywords": ["单证", "OCR", "PDF解析", "报关单"],
  "summary": "从报关单PDF/图片中提取结构化字段",
  "strategy": [
    "接受 PDF/图片，输出 {品名, 数量, 金额, HS编码}",
    "置信度 < 0.9 时标记人工复核"
  ],
  "avoid": [
    "不要对扫描件和电子PDF用同一个pipeline",
    "不要把外币金额做汇率转换（由下游节点处理）",
    "不要假设所有单证都有HS编码字段"
  ],
  "validation": "字段完整率 > 98%"
}
```

**为什么需要双形态？**

EvoMap 团队的实验（4590 次受控实验）表明：
- 完整 Skill 文档（~2500 token）注入模型后，性能反而**低于**无指导基线
- Gene 对象（~230 token）稳定**高于**基线 3pp
- 不是因为"短就是好"——把 Skill 截短到同样 token 仍然打不到 Gene 的高度
- 关键在于**形态**：strategy（策略）> summary（摘要）> overview（概述）
- AVOID 警告的控制效果最强——失败经验的最佳沉淀形态不是日志，而是蒸馏过的警告

**模型不是在"阅读文档"，而是在有限推理预算里寻找"下一步该怎么做、什么必须避免"。**

因此：
- 技术方在编辑器和管控后台里看到的是 Human Doc（完整、可审计、可理解）
- AI 在生成方案时消费的是 Model Gene（紧凑、面向控制、高信号密度）
- 两者由同一份底层数据派生，Gene 是 Human Doc 的蒸馏产物，但不是简单的截短

**Gene 的来源**：
1. Skill 首次注册时，LLM 从 Human Doc 中蒸馏出初始 Gene
2. 技术方批注 → 蒸馏为新的 strategy/AVOID 条目 → 追加到 Gene
3. 执行失败 → 蒸馏为 AVOID 警告 → 追加到 Gene
4. 多次成功执行 → Gene 中的 strategy 标记为 validated

Gene 不是写一次就不动了，它随使用**持续进化**。详见 [`product-strategy.md`](./product-strategy.md) 第六章"数据飞轮（Gene 进化模型）"。

## 六、FlowAgent 节点与 Skill 的关系

### 6.1 关系模型

```
FlowAgent 节点  ←→  Skill 引用（0 或 1 个）
                         │
                         ↓
                    Skill 平台上的 Skill
                    （可以是原子 Skill，也可以是 Skill 编排）
```

| 问题 | 答案 |
|------|------|
| 节点必须绑定 Skill 吗？ | **不是**。早期大部分节点没有对应 Skill，纯文本描述就够了 |
| 谁来绑定？ | **技术方**。AI 可以推荐，但最终由技术方确认 |
| 绑定后节点会变吗？ | 节点的输入/输出会自动对齐 Skill 的 schema，但业务描述不变 |
| 一个节点能绑多个 Skill 吗？ | **不能**。如果需要多个 Skill，应该在 Skill 平台上创建一个编排 |
| 一个 Skill 能被多个节点引用吗？ | **能**。同一个 Skill 不同参数（如"入境申报"和"出境申报"都用"海关申报 v3"） |

### 6.2 四种绑定状态

| 状态 | 含义 | 流程图显示 |
|------|------|-----------|
| **未绑定** | 节点只有文本描述，没有对应 Skill | 普通节点 |
| **AI 推荐** | AI 建议了一个 Skill，技术方还没确认 | 节点上显示推荐标签 |
| **已绑定** | 技术方确认了 Skill 绑定，schema 已对齐 | 节点上显示 Skill 名称和版本 |
| **不兼容** | 绑定了 Skill 但 schema 不匹配（Skill 升级后） | 节点上显示警告 |

### 6.3 粒度对齐原则

```
FlowAgent 节点粒度 = Skill 对外 schema 粒度 = 业务可验收粒度
                    ≠ Skill 内部步骤粒度
                    ≠ API 调用粒度
```

FlowAgent 的流程图粒度，和 Skill 平台的"对外暴露粒度"对齐，而不是和 Skill 的"内部实现粒度"对齐。

## 七、三个产品的职责边界

```
┌─────────────────────────────────┐
│         FlowAgent               │
│  "做什么"                        │
│                                 │
│  • 业务需求 → 结构化方案蓝图      │
│  • 节点 = 业务步骤               │
│  • 人机分工标注                   │
│  • Skill 推荐和绑定（引用）       │
│  • 不关心 Skill 内部怎么实现      │
└──────────────┬──────────────────┘
               │ Skill 引用（skillId + version + parameterMapping）
               ▼
┌─────────────────────────────────┐
│        Skill 平台               │
│  "用什么做"                      │
│                                 │
│  • Skill 注册（schema + 评估）   │
│  • Skill 编排（多 Skill 组合）   │
│  • Skill 版本管理               │
│  • Skill 测试和准确率指标        │
│  • 对外暴露统一 schema           │
│  • 内部实现对 FlowAgent 不透明   │
└──────────────┬──────────────────┘
               │ 可执行 Skill 定义
               ▼
┌─────────────────────────────────┐
│        执行引擎                  │
│  "怎么做"                        │
│                                 │
│  • 按 FlowAgent 蓝图编排 Skill   │
│  • 调用 Skill 平台的运行时 API   │
│  • 处理人工确认节点的暂停/恢复    │
│  • 执行日志和状态回调             │
└─────────────────────────────────┘
```

**FlowAgent 定义"做什么"，Skill 平台定义"用什么做"，执行引擎负责"怎么做"。**

三者之间的数据流：

| 从 → 到 | 传递什么 | 举例 |
|---------|---------|------|
| FlowAgent → Skill 平台 | 查询可用 Skill、获取 schema | "有没有能做合规校验的 Skill？" |
| Skill 平台 → FlowAgent | Skill 列表、schema、测试指标 | "合规校验 v2.1，准确率 98%，输入/输出 schema 如下" |
| FlowAgent → 执行引擎 | 方案蓝图 JSON（含 Skill 绑定） | 完整的 DAG + 每个节点绑定的 skillId |
| 执行引擎 → Skill 平台 | Skill 调用请求 | "执行 Skill '合规校验 v2.1'，输入数据如下" |
| 执行引擎 → FlowAgent | 执行状态、日志、评估结果 | "合规校验节点执行完成，结果：不通过" |

## 八、分阶段交互深度

| 阶段 | FlowAgent ↔ Skill 平台 | 用户体验 |
|------|------------------------|---------|
| **当前** | 无交互。节点是纯文本 | 技术方脑补对应的 Skill |
| **Phase 2 早期** | **只读查询**。搜索 Skill 注册表，AI 推荐匹配 | 节点上显示"建议使用 XX Skill" |
| **Phase 2 中期** | **参数映射**。绑定后自动校验 schema 兼容性 | 不兼容时提示技术方调整 |
| **Phase 3** | **试运行联动**。FlowAgent 发起试运行，Skill 平台用模拟数据执行 | 业务方看到交互预览 |

## 九、to B 与 to P 的 Skill 不一致

### 9.1 本质区别

| 维度 | to P（平台通用 Skill） | to B（企业私有 Skill） |
|------|----------------------|----------------------|
| **谁创建** | 平台方 | 企业技术方 |
| **谁维护** | 平台方 | 企业自己 |
| **内部可见性** | 黑盒，用户只看 schema | **白盒**，企业能看到完整逻辑、能修改 |
| **规则来源** | 通用规则（行业标准） | 企业私有规则（内部制度、历史经验） |
| **数据依赖** | 无，或依赖公开数据 | 依赖企业私有数据（内部 API、数据库） |
| **测试** | 平台方用通用数据测试 | 企业用**自己的真实数据**测试 |
| **版本管理** | 平台统一升级，企业被动接受 | 企业自主控制升级节奏 |
| **质量保证** | 平台方负责 | 企业自己负责 |

to P 的 Skill 追求广泛适用性（"PDF 解析"谁都能用），to B 的 Skill 绑定了企业私有数据和业务规则（"按我们公司的制度做合规校验"）。企业必须能看到内部逻辑、能审计、能修改——这对 to B 的交付验证和溯源是刚需。

### 9.2 企业私有 Skill 的三种来源

**来源 1：基于 to P Skill 的定制**

```
平台通用 Skill "PDF 解析"
  ↓ 企业定制
企业私有 Skill "报关单解析"
  = PDF 解析 + 企业特有的字段映射规则 + 企业特有的校验逻辑
```

大部分企业私有 Skill 是**通用能力 + 企业规则**的组合。

**来源 2：企业自己开发**

```
企业私有 Skill "内部 ERP 对接"
  = 调用企业内部 API，完全私有，和平台无关
```

**来源 3：从 FlowAgent 方案中沉淀**

```
FlowAgent 方案 "报关流程" 确认后
  → 技术方在 Dify 中搭建了"合规校验"节点
  → 跑了 3 个月，稳定了
  → 反向注册到 Skill 平台，成为企业私有 Skill
```

Skill 不是先有的，而是从实践中长出来的。

### 9.3 Skill 平台的分层架构

```
Skill 平台
├── 平台通用层（to P）
│   ├── 标准 Skill 库（平台方维护）
│   ├── 统一 schema 规范
│   └── 平台级测试和质量保证
│
├── 企业定制层（to B）
│   ├── 基于通用 Skill 的定制（通用能力 + 企业规则）
│   │   ├── 规则配置界面（业务方能看懂、能修改）
│   │   └── 企业私有数据连接
│   │
│   ├── 企业自建 Skill（纯私有）
│   │   ├── 白盒：企业能看到完整逻辑
│   │   ├── 企业自主版本管理
│   │   └── 企业自己的测试数据和质量标准
│   │
│   └── 从方案沉淀的 Skill（实践中长出来的）
│       ├── FlowAgent 确认方案 → 技术方搭建 → 稳定后注册
│       └── 自带历史执行数据和准确率指标
│
└── 社区共享层（可选）
    └── 企业脱敏后共享的 Skill（付费/免费）
```

### 9.4 对 FlowAgent 的影响

FlowAgent 不需要区分 Skill 是 to P 还是 to B——它只看对外 schema。但 AI 推荐 Skill 时应该**先搜企业私有 → 再搜平台通用**，因为企业私有 Skill 更贴合业务。

## 十、Workflow 与 Agentic 中 Skill 的不同角色

Skill 在两种任务类型中扮演的角色完全不同。

### 10.1 Workflow 中的 Skill：预先绑定

Workflow 的节点和 Skill 是**确定性的绑定关系**——在方案设计阶段就确定了"第 3 步用合规校验 Skill v2.1"。

```
节点 "合规校验" ──绑定──▶ Skill "合规校验 v2.1"

设计时确定：哪个节点用哪个 Skill
执行时确定：按绑定关系调用，不会变
```

用户（业务方 + 技术方）在方案中审查的是：**这个节点绑定的 Skill 对不对、参数映射对不对。**

### 10.2 Agentic 中的 Skill：授权而非绑定

Agentic 任务中，用户做的不是"绑定"，而是**授权**——决定"给不给 Agent 这个能力"。

```
策略卡片 "可用 Skill 列表"：
  ✅ 网页数据采集
  ✅ 内容生成
  ✅ 小红书发帖
  ❌ 付费投放（用户不授权这个能力）
```

是否调用、什么时候调用、怎么调用——这些不是用户在方案设计阶段决定的，而是：

| 决策 | 谁决定 | 什么时候 |
|------|--------|---------|
| **给不给这个能力** | 用户（业务方 + 技术方共同确认） | 方案设计阶段 |
| **是否调用** | Agent 自主判断 | 执行时，根据当前步骤的需要 |
| **怎么调用（参数）** | Agent 自主决定 + 用户给的策略约束 | 执行时，根据上下文和约束 |
| **调用结果好不好** | 三层评估体系 | 执行后，工具级 → 步骤级 → 目标级 |

**类比**：Workflow 中的 Skill 像"工具箱里的螺丝刀，图纸上标好了第 3 步用它"。Agentic 中的 Skill 像"给员工配的工具包，员工自己判断什么时候用哪个"。

### 10.3 对策略卡片的影响

策略卡片中"可用 Skill 列表"的交互应该是：

```
可用技能                              [从 Skill 平台添加]

┌──────────────────────────────────────────────┐
│ ✅ 网页数据采集          平台通用 · v3.0      │
│    采集指定网站的结构化数据                     │
│                                              │
│ ✅ 内容生成              平台通用 · v2.1      │
│    根据主题和风格要求生成文本内容               │
│                                              │
│ ✅ 小红书发帖            企业私有 · v1.3      │
│    发布图文/视频到指定小红书账号               │
│                                              │
│ ☐ 付费投放              企业私有 · v1.0      │
│    在小红书投放付费广告                        │
│    ⚠️ 涉及预算，需要额外授权                  │
└──────────────────────────────────────────────┘
```

业务方关心的是"我要不要给 Agent 花钱的能力"，技术方关心的是"这些 Skill 的 schema 和质量够不够"。两个角色审查的维度不同，但都是在做**授权决策**。

### 10.4 对比总结

| 维度 | Workflow 中的 Skill | Agentic 中的 Skill |
|------|--------------------|--------------------|
| 关系 | 节点 **绑定** Skill（1:1） | 任务 **授权** Skill 列表（1:N） |
| 决定时机 | 方案设计阶段 | 方案设计阶段（授权）+ 执行时（调用） |
| 用户决策 | "这步用哪个 Skill" | "给不给 Agent 这个能力" |
| Agent 自主性 | 无——按图执行 | 有——自主选择调用哪个、怎么调用 |
| 参数 | 设计时映射好 | 执行时 Agent 根据上下文决定 |
| 约束 | 节点的输入/输出 schema | 用户给的策略 + 约束条件 |
| 评估 | 工具级（Skill 自带） | 三层（工具级 + 步骤级 + 目标级） |

## 十一、Skill 平台产品设计

> 以下内容整合自 FlowAgent 产品文档第六章。

### 11.1 三层可见性

| 层级 | 来源 | 可见范围 | 举例 |
|------|------|---------|------|
| **平台通用** | 平台方创建和维护，通过项目积累沉淀 | 所有企业用户 | "网页数据采集"、"文本生成"、"PDF 解析" |
| **社区共享** | 企业上传的不涉及商业机密的 Skill | 所有企业用户（可付费/免费） | "跨境电商报关通用流程"、"标准合同审核" |
| **企业私有** | 企业内部开发的涉及商业机密的 Skill | 仅该企业用户 | "内部 ERP 对接 API"、"专有风控模型" |

业务方登录 FlowAgent 后，AI 翻译时能检索到的 Skill 范围 = **平台通用 + 社区共享 + 该企业私有**。

### 11.2 FlowAgent 与 Skill 平台的集成定位

FlowAgent 的定位是**"翻译 + 编排"**，与 Skill 平台深度集成，而非自建 Skill 运行时：

| 职责 | FlowAgent | Skill 平台 |
|------|-----------|-----------|
| 需求翻译 | 自然语言 → 结构化方案 | — |
| Skill 匹配 | 根据方案节点推荐合适的 Skill | — |
| Flow 编排 | 定义节点顺序、人机分工、数据流转 | — |
| Skill 注册 | — | API schema、版本管理、权限控制 |
| Skill 运行 | — | 调用执行、日志采集、错误处理 |
| 试运行 | 发起试运行请求 + 展示结果 | 实际执行试运行 |
| 知识沉淀 | 方案模板、人机分工规则、失败记录 | Skill 使用统计、性能指标 |

### 11.3 Skill 标准化的分阶段演进

| 阶段 | Skill 标准化程度 | FlowAgent 的能力 | 业务方体验 |
|------|-----------------|-----------------|-----------|
| **当前** | 只有名字和描述 | 方案蓝图中标注"建议使用 XX Skill" | 看到流程图，技术方手动搭建 |
| **Phase 2** | 有 I/O schema | AI 翻译时自动匹配 Skill，生成可执行 Flow 定义 | 看到流程图 + 每步关联的具体 Skill |
| **Phase 3** | 完整标准化（含沙箱/测试用例） | 生成 Flow 后可直接试运行 | 看到流程图 + 试运行结果 |

### 11.4 企业 Skill 上传意愿

| 因素 | 促进上传 | 阻碍上传 |
|------|---------|---------|
| **商业价值** | 付费 Skill 带来收入 | 核心竞争力泄露 |
| **社区效应** | 上传越多 → 生态越丰富 → 自己也受益 | 维护成本 |
| **平台激励** | 上传者获得平台积分/优先推荐 | — |

预期路径：早期以平台通用 Skill 为主 → 中期鼓励社区共享非敏感 Skill → 长期形成 Skill 市场生态。

## 十二、Skill 热替换与灰度机制

> 2026-04-23 新增。Agentic 项目运行周期长、外部环境变化快，需要在不停止执行的情况下更换或升级 Skill。

### 12.1 逻辑名 → 实例的间接层

当前架构中方案节点直接绑定 Skill 的具体版本（如"合规校验 v2.1"）。这意味着升级 Skill 必须修改方案——对 Workflow 可以接受（低频变更），对 Agentic 太重了。

解决方案是在方案绑定和实际调用之间增加一个**间接层**：

```
方案节点 ──绑定──▶ Skill 逻辑引用（逻辑名）──解析──▶ Skill 实例（具体版本）
                                                │
                                      解析规则（运行时可修改）：
                                      ├─ 默认：用方案绑定的版本
                                      ├─ 灰度：30% 流量用新版本
                                      └─ 强制：全部切到新版本
```

方案中绑定的是 `skillRef: "compliance-check"`（逻辑名），而非 `skillId: "compliance-check-v2.1"`。Skill 平台维护逻辑名到具体版本的**解析规则表**，执行引擎每次调用前查表获取实际版本。

### 12.2 解析规则表

| 逻辑名 | 默认版本 | 灰度规则 | 回退版本 |
|--------|---------|---------|---------|
| compliance-check | v2.1 | 30% → v3.0（试用中） | v2.0 |
| content-generate | v2.3 | — | v2.2 |
| xhs-publish | v1.3 | — | v1.2 |

规则表的修改权限在技术方，修改操作属于 Layer 3 调整（见 `flowagent-product.md` 3.2.7），需要技术方确认。

### 12.3 热替换的前提条件

Skill 热替换不是无条件的，必须满足：

| 条件 | 说明 |
|------|------|
| **输入 schema 兼容** | 新版 Skill 的输入 schema 是旧版的超集（向后兼容） |
| **输出 schema 兼容** | 新版 Skill 的输出 schema 包含旧版所有字段（可以新增，不能删除） |
| **质量契约满足** | 新版 Skill 的输出 quality_signals 满足下游节点的最低要求 |

不满足兼容性的升级（breaking change）必须走 Layer 4 调整——回编辑器创建新版本方案。

### 12.4 灰度发布流程

```
技术方决定试用新版 Skill
    │
    ▼
在解析规则表中设置灰度比例（如 30%）
    │
    ▼
执行引擎按比例分流：
  70% 的任务调用旧版 v2.1
  30% 的任务调用新版 v3.0
    │
    ▼
灰度期间持续对比两组的工具级评估指标
    │
    ├─ 新版更好 → 逐步提高灰度比例 → 全量切换
    ├─ 新版持平 → 延长灰度观察
    └─ 新版更差 → 一键回退到旧版
```

灰度数据自动汇总为 Skill 升级报告，技术方据此决定是否全量切换。

### 12.5 对四种绑定状态的扩展

原有四种绑定状态（未绑定/AI推荐/已绑定/不兼容）基础上，增加灰度相关状态：

| 状态 | 含义 | 流程图显示 |
|------|------|-----------|
| **灰度中** | 已绑定，但有新版本在灰度测试 | 节点上显示 🔄 + 灰度比例 |
| **待切换** | 灰度完成，等待技术方确认全量切换 | 节点上显示推荐升级标签 |

## 十三、开放问题

以下问题尚未定论，需要在实践中验证：

| 问题 | 思考方向 |
|------|---------|
| **Skill 编排在哪里定义？** | 在 Skill 平台上定义（推荐），还是在 FlowAgent 中通过子流程定义？如果在 FlowAgent 中定义，FlowAgent 就不只是"设计层"了 |
| **Skill 版本升级后怎么办？** | Skill v2 → v3，输出 schema 变了，已绑定的 FlowAgent 方案怎么处理？需要版本兼容策略 |
| **跨企业 Skill 的信任问题** | 企业 A 的方案绑定了社区共享的 Skill，这个 Skill 的质量谁保证？需要 Skill 评级/认证机制 |
| **Skill 粒度的灰色地带** | "发送通知"算一个 Skill 吗？它的输出（"通知已发送"）业务方能验收，但粒度很小。是否需要区分"轻量 Skill"和"重量 Skill"？ |
| **Agentic 任务中 Skill 的预算控制** | 涉及付费的 Skill（如广告投放），授权时是否需要设置预算上限？这和约束条件中的"预算"是否重复？ |
| **Skill 从 to P 到 to B 的定制流程** | 企业基于通用 Skill 定制时，规则配置界面应该长什么样？业务方能直接配置，还是必须技术方介入？ |
