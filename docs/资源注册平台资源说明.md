# 资源注册平台资源说明

本文专门说明资源注册平台负责登记哪些资源、每类资源里应该维护哪些信息，以及这些资源和 FlowAgent / JobSpec 的边界。

核心原则：

- 资源注册平台维护“平台可复用能力”的本体。
- FlowAgent 技术配置页维护 JobSpec 草稿，只选择或引用资源 code。
- JobSpec 不重复保存资源完整配置。
- 发布前由平台注册表和 JobSpec 一起做 readiness 校验。

## 1. 资源注册平台负责什么

资源注册平台回答的是：

> 平台里已经有哪些可被 Job / Task 复用的能力？

它不直接描述某一个业务流程怎么跑。业务流程由 JobSpec 的 `tasks` 和 `flow` 编排。

资源注册平台主要管理：

| 资源 | 作用 | JobSpec 中如何引用 |
| --- | --- | --- |
| Secret | 凭证引用，不保存明文 | `secret_refs` |
| Tool | 可被 Task 调用的外部动作或接口 | `tool_codes` |
| Skill | Agentic Task 的业务能力说明 | `skill_codes` |
| ContextSource | 上下文来源目录 | 被 ContextPolicy 引用 |
| ContextPolicy | TaskRun 上下文打包策略 | `context_policy_code` |
| RuntimeProfile | 执行器配置 | `runtime_profile_code` |
| ReviewPolicy | 人工审核派单与处理规则 | `review_policy_code` |
| TriggerDefinition | 外部或平台内部如何启动 Job | `triggers` |

## 2. Secret

Secret 是凭证引用。平台只保存凭证来源，不保存明文。

它解决的问题：

> Tool 或 Trigger 调外部系统时，用哪个凭证引用？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | Secret 引用编码，例如 `sharepoint-api-credential` |
| `name` | 展示名称 |
| `provider` | 凭证来源，例如 `env`、`external_ref` |
| `env_key` | provider 为 `env` 时，对应环境变量名 |
| `external_ref` | 外部 Secret Manager / Vault 引用 |
| `scope` | 授权范围，例如 `sharepoint.read` |
| `risk_level` | 风险等级 |
| `rotation_policy` | 轮换策略 |
| `status` | `active`、`disabled`、`rotating`、`revoked` |

不应该填写：

- 明文 token。
- 明文 password。
- 明文 API Key。

示例：

```yaml
code: sharepoint-api-credential
name: SharePoint API 凭证
provider: env
env_key: SHAREPOINT_API_KEY
scope:
  - sharepoint.read
risk_level: high
status: active
```

FlowAgent 中只引用：

```yaml
secret_refs:
  - sharepoint-api-credential
```

## 3. Tool

Tool 是可被 Task 调用的外部动作或接口。

它解决的问题：

> 当前 Task 可以调用哪些平台受控动作？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | Tool 编码，例如 `sharepoint-file-download` |
| `name` | 工具名称 |
| `type` | 工具类型，当前稳定生产以 `http` 为主 |
| `description` | 工具用途、输入、输出、副作用说明 |
| `permission_scopes` | 权限范围 |
| `risk_level` | 风险等级 |
| `secret_refs` | Tool 依赖的 Secret code |
| `input_schema` | Tool 调用入参结构 |
| `output_schema` | Tool 返回结构 |
| `config` | Tool 真实执行配置，例如 URL、method、auth |
| `status` | `draft`、`published`、`disabled` |

示例：

```yaml
code: sharepoint-file-download
name: 下载 SharePoint 文件
type: http
description: 根据文件 URL 下载 GSDS PDF，并返回临时文件路径。
permission_scopes:
  - sharepoint.read
secret_refs:
  - sharepoint-api-credential
input_schema:
  type: object
  required:
    - sharepoint_file_url
  properties:
    sharepoint_file_url:
      type: string
output_schema:
  type: object
  required:
    - pdf_file_path
  properties:
    pdf_file_path:
      type: string
config:
  method: GET
  url: https://sharepoint.example.com/download
  auth:
    type: bearer
    secret_ref: sharepoint-api-credential
status: published
```

FlowAgent 中只引用：

```yaml
tool_codes:
  - sharepoint-file-download
secret_refs:
  - sharepoint-api-credential
```

## 4. Skill

Skill 是 Agentic Task 的业务能力说明书，不是可执行程序，也不是外部接口。

它解决的问题：

> Agentic 执行器应该按什么业务方法理解和完成这个 Task？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `metadata.code` | Skill code，例如 `skill-gsds-pdf-parser` |
| `metadata.name` | 能力名称 |
| `metadata.version` | 能力版本 |
| `metadata.description` | 能力说明 |
| `target_providers` | 目标执行器，例如 `openclaw` |
| `entrypoint` | 入口说明文件，例如 `SKILL.md` |
| `type` | 通常为 `llm` |
| `permission_scopes` | 需要的上下文或能力权限 |
| `risk_level` | 风险等级 |
| `input_schema` | Skill 期望输入 |
| `output_schema` | Skill 期望输出 |
| `status` | `draft`、`published`、`disabled` |
| `package_files` | Skill 包文件快照 |
| `content_hash` | Skill 包哈希 |

示例：

```yaml
spec_version: task-platform.skill.v1
kind: AgentSkill
metadata:
  code: skill-gsds-pdf-parser
  name: GSDS PDF 字段解析
  version: 1.0.0
  description: 从 GSDS PDF 中提取 BBN、PART、颜色、状态、运输名称等字段。
target_providers:
  - openclaw
entrypoint: SKILL.md
type: llm
permission_scopes:
  - gsds.read_context
output_schema:
  type: object
  required:
    - gsds_record
status: published
```

FlowAgent 中只在 `agentic` Task 引用：

```yaml
skill_codes:
  - skill-gsds-pdf-parser
```

## 5. ContextSource

ContextSource 是上下文来源目录。

它解决的问题：

> 平台将来从哪里拿这类上下文？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | 来源编码，例如 `gsds-master-data-source` |
| `name` | 来源名称 |
| `source_type` | `manual`、`static`、`http`、`object_storage` |
| `sensitivity` | 敏感级别 |
| `config` | 解析配置，例如 HTTP URL、对象存储路径、静态内容 |

示例：

```yaml
code: gsds-master-data-source
name: GSDS 主库数据源
source_type: http
sensitivity: confidential
config:
  url: https://data.example.com/gsds/query
  method: POST
  auth:
    type: bearer
    secret_ref: gsds-db-credential
```

FlowAgent 一般不直接引用 ContextSource。它由 ContextPolicy 选择和打包。

## 6. ContextPolicy

ContextPolicy 是 TaskRun 执行前的上下文打包规则。

它解决的问题：

> 当前 Task 能看到哪些 Job 输入、上游输出和外部上下文来源？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | 策略编码，例如 `gsds-pdf-parse-context` |
| `name` | 策略名称 |
| `package_format` | 当前稳定为 `structured_json` |
| `rules.include_job_input` | 是否包含 Job 输入 |
| `rules.include_upstream_outputs` | 是否包含上游 Task 输出 |
| `rules.include_sources` | 需要解析的 ContextSource code |
| `rules.required_fields` | 必须存在的上下文字段 |
| `rules.redaction` | 脱敏规则 |
| `rules.max_payload_kb` | 最大上下文包大小 |

示例：

```yaml
code: gsds-pdf-parse-context
name: GSDS PDF 解析上下文策略
package_format: structured_json
rules:
  include_job_input: true
  include_upstream_outputs: true
  include_sources: []
  required_fields:
    - upstream.fetch-pdf.pdf_file_path
  redaction:
    patterns:
      - token
      - authorization
  max_payload_kb: 512
```

FlowAgent 中只引用：

```yaml
context_policy_code: gsds-pdf-parse-context
```

注意：`input_schema` 和 `context_policy_code` 不是一回事。

- `input_schema` 定义这个 Job 或 Task 验收什么输入结构。
- `context_policy_code` 决定运行时怎么把 Job 输入、上游输出和 ContextSource 打包给执行器。

## 7. RuntimeProfile

RuntimeProfile 是执行器配置。

它解决的问题：

> 这个 Task 由什么 Runtime 跑，超时多久，使用什么执行器参数？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | Runtime 编码，例如 `openclaw-gsds-extraction` |
| `name` | Runtime 名称 |
| `provider_type` | `openclaw`、`http_worker`、`custom_worker` |
| `timeout_seconds` | 单次执行超时时间 |
| `config` | 执行器配置 |
| `status` | `draft`、`published`、`disabled` |

示例：

```yaml
code: openclaw-gsds-extraction
name: OpenClaw GSDS 字段提取执行器
provider_type: openclaw
timeout_seconds: 600
config:
  command: openclaw
  workspace_dir: .runtime/openclaw-workspace
status: published
```

FlowAgent 中只引用：

```yaml
runtime_profile_code: openclaw-gsds-extraction
```

Task 类型和 Runtime 应匹配：

| Task 类型 | 推荐 Runtime |
| --- | --- |
| `agentic` | `openclaw` |
| `integration` | `http_worker` |
| `deterministic` | `custom_worker` |
| `human_review` | 不绑定普通 Runtime，绑定 ReviewPolicy |

## 8. ReviewPolicy

ReviewPolicy 是人工审核策略。

它解决的问题：

> 什么情况下要人审？谁审？多久审？超时怎么办？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | 审核策略编码，例如 `gsds-data-steward-review` |
| `name` | 审核策略名称 |
| `description` | 审核策略说明 |
| `applies_to` | 适用范围 |
| `rules` | 审核触发条件、审核组、SLA |
| `status` | `draft`、`published`、`disabled` |

示例：

```yaml
code: gsds-data-steward-review
name: GSDS 数据管理员复核
description: 在写入 GSDS 主库前由数据管理员确认解析字段。
applies_to:
  task_types:
    - human_review
rules:
  always_require: true
  reviewer_groups:
    - data-steward
  sla_hours: 24
status: published
```

FlowAgent 中只在 `human_review` Task 引用：

```yaml
review_policy_code: gsds-data-steward-review
```

## 9. TriggerDefinition

TriggerDefinition 是 Job 的启动入口定义。

它解决的问题：

> 哪个 API、webhook、schedule、文件到达事件或平台事件可以启动这个 Job？

应该在资源注册平台填写：

| 字段 | 含义 |
| --- | --- |
| `code` | Trigger 编码，例如 `gsds-pdf-uploaded` |
| `name` | 触发器名称 |
| `job_template_code` | 目标 JobTemplate code |
| `type` | `api`、`webhook`、`schedule` 等 |
| `description` | 触发语义 |
| `input_schema` | 触发 payload 结构 |
| `auth` | 鉴权配置 |
| `idempotency` | 幂等键配置 |
| `rate_limit` | 限流配置 |
| `status` | `draft`、`published`、`disabled` |

示例：

```yaml
code: gsds-pdf-uploaded
name: GSDS PDF 上传触发器
job_template_code: gsds-pdf-ingest
type: webhook
description: SharePoint 文件夹新增 GSDS PDF 时启动入库 Job。
input_schema:
  type: object
  required:
    - sharepoint_file_url
    - file_name
  properties:
    sharepoint_file_url:
      type: string
    file_name:
      type: string
auth:
  type: secret_ref
  secret_ref: sharepoint-webhook-secret
idempotency:
  key_path: sharepoint_file_url
status: published
```

FlowAgent 中只引用：

```yaml
triggers:
  - gsds-pdf-uploaded
```

JobSpec 的 `input_schema` 可以从 TriggerDefinition 的 `input_schema` 映射生成，但 Trigger 的鉴权、幂等和限流仍属于资源注册平台。

## 10. 生产控制能力如何落地

当前不建议第一阶段新增一批顶层资源，例如 Validator、ApprovalPolicy、AuditPolicy、DataProduct、WritePolicy、RetryResumePolicy。

更稳妥的落地方式是：

| 控制能力 | 第一阶段建议承载位置 |
| --- | --- |
| Validator | Task 的 `output_schema` 或独立 `deterministic` Task |
| ApprovalPolicy | `ReviewPolicy` 或 `human_review` Task |
| AuditPolicy | 平台默认审计、RuntimeProfile 或 Tool 配置 |
| DataProduct | `ContextSource` / `ContextPolicy` 的质量、版本、鲜度字段 |
| WritePolicy | `Tool` 能力声明和写入类 Task 的 Tool 绑定 |
| RetryResumePolicy | `RuntimeProfile.config.retry` 或 Runtime 层控制 |

只有当某类策略满足以下条件时，才考虑抽成新的顶层资源：

- 被多个 Job / Tool 复用。
- 有独立生命周期和版本。
- 需要单独审批发布。
- 由专门团队维护。
- 现有资源字段已经表达不清。

## 11. FlowAgent 技术配置页应该怎么呈现

FlowAgent 不编辑资源本体，只在 JobSpec 中选择资源 code。

推荐展示方式：

| Task 类型 | 应展示的绑定 |
| --- | --- |
| `agentic` | `runtime_profile_code`、`context_policy_code`、`skill_codes`、可选 `tool_codes` / `secret_refs` |
| `integration` | `runtime_profile_code`、`context_policy_code`、`tool_codes`、`secret_refs` |
| `deterministic` | `runtime_profile_code`、`context_policy_code`、`input_schema`、`output_schema` |
| `human_review` | `review_policy_code`、`input_schema`、`output_schema` |

不建议在 FlowAgent 全局配置页展示：

- Tool URL。
- Secret env_key。
- Trigger auth / idempotency。
- ContextSource 详细连接配置。
- Runtime 内部命令和运行目录。
- 资源策略摘要的大段说明。

这些内容应该在资源注册平台维护，FlowAgent 可以只展示只读摘要和缺失提示。

## 12. 一句话总结

资源注册平台登记“可复用能力本体”，FlowAgent 生成“JobSpec 编排草稿”。两者通过资源 code 连接：资源注册平台保证能力可信，FlowAgent 保证业务 Job 引用正确。
