# 产品战略：知识容器与自进化飞轮

> 最后更新：2026-04-10
>
> 本文档聚焦 FlowAgent 产品矩阵的战略层思考——知识容器为什么是核心壁垒、自进化飞轮如何运转、以及从"工具"到"平台"的演进逻辑。
>
> 产品矩阵全景见 [`产品矩阵.md`](./产品矩阵.md)，FlowAgent 功能设计见 [`FlowAgent产品说明.md`](./FlowAgent产品说明.md)。

---

## 一、核心命题

FlowAgent 的工具能力（AI 翻译）可以被替代，但**沉淀在里面的企业私有知识**无法被替代。

| 维度 | 说明 |
|------|------|
| **来源** | 不依赖用户主动填写，而是从"使用产品"的过程中自然采集 |
| **格式** | 结构化的方案骨架 + 关键决策 + 人机分工标注，不是非结构化文档 |
| **壁垒** | 是企业私有的、经过技术验证的决策记录，竞品无法获取 |
| **价值** | 用得越多 → 知识越丰富 → AI 生成越准确 → 技术方审核越轻松 → 用得更多 |

**工具解决效率，知识解决质量，效率+质量构成飞轮。**

## 二、知识的六种形态

| 形态 | 内容 | 举例 |
|------|------|------|
| **已验证方案模板** | 技术方 confirmed 的完整方案（骨架 + 关键决策 + 人机分工） | "进出口报关"的 6 步 workflow，合规校验用规则引擎不用 AI |
| **人机分工规则** | 哪种类型的步骤应该由谁执行的经验总结 | "数据校验后必须人工确认"在金融行业适用但在电商不一定 |
| **企业特化约束** | 特定企业的合规要求、技术栈限制、审批链路 | "所有对外发布必须经过两级审批"，"只能用内部部署的模型" |
| **失败记录** | 方案执行后的异常归因，区分搭建质量/链路设计/环境问题 | "合规校验节点用 AI 判断导致 30% 误判 → 改为规则引擎" |
| **企业 Skill 库** | 企业私有的原子能力注册表（来自 Skill 平台） | "内部关税查询 API"、"合规校验规则引擎 v2" |
| **验证记录** | 知识工作台中对业务规则/数据的分析结果，绑定到具体方案 | "审批规则验证：发现 3 类未覆盖情况（外币/异常值/免审）" |

企业 Skill 库来自外部 Skill 平台，但对 FlowAgent 而言，它是知识容器的一部分——AI 翻译时不仅参考历史方案，还参考企业已有的 Skill 来选择最合适的实现方式。

验证记录来自知识工作台。每次用户用真实数据验证业务规则，发现的边界情况和异常模式都会沉淀下来：
- **方案层面**：下次修改同一方案时，能看到"上次验证发现了哪些问题，哪些已处理"
- **知识层面**：跨方案积累后，AI 能归纳出"金额类规则常见的漏洞模式"，在新方案中主动提醒

### 知识的双形态原则（Gene 理念）

> 参考 EvoMap/清华 Gene 研究（2026）：给模型用的经验对象应按"控制密度"设计，而非按"文档完整性"设计。完整 Skill 文档（~2500 token）反而低于无指导基线，~230 token 的 Gene 对象稳定胜出。

上述六种知识形态，每一种都存在**双形态**：

| | Human Doc（给人看） | Model Gene（给模型用） |
|---|---|---|
| **设计目标** | 完整性、可理解性、可审计 | 控制密度、可匹配、可进化 |
| **内容结构** | overview + workflow + pitfalls + examples + API notes | keywords + summary + strategy + AVOID |
| **典型长度** | 500-3000 token | 100-300 token |
| **谁消费** | 技术方（编辑器/管控后台查看） | AI（生成方案时注入 prompt） |

**核心洞察**：给人类工程师看的完整文档，塞进模型的推理预算后，反而稀释控制信号。模型不是在"阅读文档"，而是在有限 token 预算里寻找"下一步该怎么做、什么必须避免"。因此，知识容器的写入端产生的是 Human Doc，但读取端（AI 生成时）消费的是蒸馏后的 Gene 对象。

## 三、知识沉淀机制

知识沉淀的来源**不是业务方填表**，而是系统和技术方在日常使用中自然产生：

| 来源 | 能判断什么 | 沉淀什么 |
|------|-----------|---------|
| **系统自动采集** | 节点执行成功/失败、耗时、错误日志 | 执行指标数据（Phase 2 对接执行层后） |
| **技术方** | 失败归因（搭建质量 vs 链路设计 vs 环境问题） | 异常归因标注、评审批注、最佳实践 |
| **业务方** | 最终业务结果是否达预期 | 通过下一次翻译对话自然反馈（"上次方案效果不好，想调整..."） |

## 四、双层知识架构

| 层级 | 内容 | 来源 | 更新方式 |
|------|------|------|---------|
| **静态知识** | 行业模板、最佳实践、API 文档、SOP | 人工录入 + SOP 文档自动提取 | 低频，人工审核后入库 |
| **动态知识** | 已确认方案模板、执行日志、评审批注、异常归因 | 系统自动采集 + 技术方标注 | 随使用自动积累 |

## 五、AI 翻译如何参考知识

AI 翻译新场景时，参考的是**技术方已确认通过的方案**（状态为 confirmed），而不是所有历史数据。沉淀格式为"方案骨架 + 关键决策点"：

```
场景: 进出口报关自动化
类型: workflow
骨架: [单证采集, 合规校验, 申报提交, 状态跟踪, 异常处理]
关键决策:
  - 合规校验: 用规则引擎而非AI判断，因为合规标准是确定性的
  - 异常处理: 设了人工确认节点，因为海关驳回原因复杂需要人判断
确认人: tech_reviewer_id
确认时间: 2026-04-01
```

参考逻辑：检索与新需求相似的已确认方案 → 提取其骨架和关键决策作为 AI 生成时的 few-shot 参考 → 技术方审核时也能看到"AI 参考了哪个历史方案"。

## 六、自进化飞轮

> 知识容器不仅是静态存储，更是驱动 AI 持续进化的飞轮。类比员工经验积累：新员工做 50 次才能形成的经验，FlowAgent 通过结构化数据沉淀压缩到 5 次。

### 三层进化

**第一层：记忆（记住用户改了什么）**

每次用户确认方案，系统记录 AI 初版 vs 用户终版的 Diff：

```
场景：客户投诉处理
AI 犯的错：
  ① 漏了升级路径
  ② 把人工回访标成了 AI 自动
  ③ 缺少满意度回收
用户的修正：具体改了什么
```

下次有人再问类似场景，AI 不会犯同样的错。实现方式：将修正后的方案作为 few-shot 放进 prompt。

**第二层：归纳（从个案中提炼规则）**

从多次修正中归纳通用规则：

```
观察到的现象：
- 投诉处理：用户把"自动回访"改成了"人工回访"
- 售后退款：用户把"自动审批"改成了"人工审批"
- 合同审核：用户把"AI 判断合规"改成了"法务确认"

归纳出的规则：
→ 涉及客户直接沟通、资金操作、法律合规的步骤，默认标记为人工执行
```

归纳可以用 LLM 完成——定期把积累的修正记录丢给 AI 总结规则，再写回 prompt。这就是"人机分工规则"的来源。

**第三层：判断（知道什么时候该问、什么时候不该问）**

```
初期：AI 对很多节点都不确定，标记很多黄点
中期：AI 通过积累的规则和案例，大部分节点都能确定，只标记真正需要人决策的地方
后期：AI 能主动质疑需求——"你说要全自动处理退款，但根据过往案例，
      超过 5000 元的退款都需要主管审批，你确定要全自动吗？"
```

从"被动回答"到"主动建议"的进化。

### 数据飞轮（Gene 进化模型）

```
┌─────────────────────────────────────────────┐
│              用户使用平台                      │
│  输入需求 → 生成方案 → 编辑修正 → 确认方案      │
│  管控后台 → 执行监控 → 失败处理 → 批注/质疑     │
└──────────────────┬──────────────────────────┘
                   │ 自动收集
                   ▼
┌─────────────────────────────────────────────┐
│           数据沉淀层（Human Doc 形态）          │
│  ① 场景案例库：每次确认的最终方案（带场景标签）    │
│  ② 修正记录：AI 初版 vs 用户终版的 Diff          │
│  ③ 操作行为：用户跳过了哪些标记、改了哪些节点     │
│  ④ 执行失败日志：完整的错误链路和上下文           │
│  ⑤ 技术批注原文：批注/质疑/建议的完整内容         │
└──────────────────┬──────────────────────────┘
                   │ Gene 蒸馏（LLM 辅助 + 技术方确认）
                   ▼
┌─────────────────────────────────────────────┐
│           Gene 池（Model Gene 形态）            │
│  ① Skill Gene：每个 Skill 的控制片段            │
│     keywords + strategy + AVOID + validation  │
│  ② 场景 Gene：某类场景的通用策略和禁忌           │
│     "报关场景必须校验HS编码位数一致性"            │
│  ③ 通用 Gene：跨场景归纳的全局规则               │
│     "涉及客户沟通的步骤默认标记人工确认"          │
│  每个 Gene ~200-300 token，高控制密度            │
└──────────────────┬──────────────────────────┘
                   │ 匹配注入（keywords 匹配 + 作用域过滤）
                   ▼
┌─────────────────────────────────────────────┐
│              生成增强层                        │
│  生成 prompt = 基础指令                        │
│              + 匹配的方案模板（few-shot）        │
│              + 匹配的 Skill Gene（strategy）    │
│              + 匹配的场景 Gene（AVOID 警告）     │
│              + 通用 Gene（全局规则）             │
│  总 Gene 注入预算 ≤ 500 token                  │
└──────────────────┬──────────────────────────┘
                   │ 执行结果反馈
                   ▼
┌─────────────────────────────────────────────┐
│              Gene 进化层                       │
│  成功 → strategy 标记 validated                │
│  失败 → 蒸馏新 AVOID → 追加到对应 Gene          │
│  批注 → 蒸馏 strategy/AVOID → 技术方确认后入库   │
│  跨方案归纳 → 相同 AVOID 出现 3+ 次 → 升为通用   │
└─────────────────────────────────────────────┘
```

**关键变化**（vs 之前的设计）：
- 知识提炼层从"归纳完整规则"变为"蒸馏 Gene 控制片段"——更短、更精准、更面向模型决策
- 失败经验从"存日志"变为"蒸馏 AVOID 警告"——EvoMap 实验表明这是最有效的失败复用形态
- 注入方式从"把规则文本放进 prompt"变为"匹配 Gene 对象作为 System Instruction"——控制密度提升 10 倍
- Gene 池本身是可进化的——每次执行结果和批注都可能触发 Gene 更新

**这是产品矩阵作为 to B 产品的核心护城河**：竞品可以抄 UI，但抄不走积累的 Gene 池。Gene 池是企业私有的、经过验证的、持续进化的控制资产。

### 分阶段实现

| 阶段 | 做什么 | 前置条件 |
|------|--------|---------|
| **Demo（当前）** | 手动准备 2-3 个 few-shot 示例 + 手动写规则放进 prompt | 无 |
| **有后端后** | 自动存储修正 Diff + 批注；引入 Gene 数据模型，手动蒸馏首批 Gene | Supabase |
| **数据积累后** | LLM 辅助蒸馏：批注 → Gene 片段（技术方确认后入库），动态 Gene 匹配注入 | 10+ 确认案例 |
| **成熟期** | 全自动 Gene 进化循环：执行结果 → 蒸馏 → 注入 → 验证 → 更新；AI 基于 Gene 池主动追问 | 50+ 确认案例 |

## 七、知识容器升级方向

> 详见 [`产品矩阵.md`](./产品矩阵.md) 第四章。

当前设计聚焦于"方案知识"（第二层），升级方向是三层架构：

- **业务领域知识**（底层）：行业规则、企业约束、数据关系——不绑定方案，是所有方案的公共基础
- **方案知识**（中层）：已验证方案、修正记录、人机分工规则——现有设计
- **运行知识**（上层）：执行日志、配置变更轨迹、效果关联——来自执行层和管控后台

三层之间是双向流动的，不只是"沉淀→参考"的单向链路。

## 八、竞争壁垒分析

**短期壁垒**：双角色协作设计（业务方 + 技术方在同一平台上）。市面上没有产品这么做。

**长期壁垒**：知识容器。竞品的知识库是手动上传的静态文档；我们的知识是从使用中自然生长的、经过验证的、和执行效果关联的活数据。

**终极壁垒**：配置 x 效果的关联数据。当企业积累了"什么配置在什么场景下效果最好"的数据后，这些数据本身就是无法迁移的资产。

### 潜在风险

| 风险 | 应对 |
|------|------|
| 执行平台向上游延伸（Dify/Coze 加入自然语言需求功能） | 它们的基因是执行，做好双角色协作和知识沉淀难 |
| BPMN 工具向下游延伸 | 它们的基因是画图，缺乏 AI 翻译能力和知识架构 |
| 大厂内部自建 | FlowAgent 的知识沉淀可跨企业积累通用规则，自建工具只有单企业数据 |
| "直接执行"路线胜出 | 行业数据显示短期内不会发生；即使发生，知识容器仍有独立价值 |
